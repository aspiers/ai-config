A needs-based comparison of Adam Spiers’ ggmx/ggmxd branch mixer with worktrunk-sync, git-machete, and representative FOSS contenders for multiple concurrent short- and long-lived work streams.

ggmx + ggmxd

Verdict: retain as a small, local integration-testing primitive. It solves a real problem the stack managers do not: repeatedly rebuilding a disposable branch from a base plus an arbitrary ordered set of independent branches. It does not solve branch freshness, dependency propagation, worktree orchestration, or publication.

GitHub stars105 as of 11 August 2026 UTC
Maintenance25 repository commits in the 12-month window; latest mixer core change 1 April 2020; safety/agent documentation updated 9 July 2026
LicenceGPL-3.0-or-later
Latest releaseNo tagged release

Domain fit

git mix stores ordered branch sets under mixdown.<target> in Git config; ggmx is its short wrapper. git mixdown, wrapped by ggmxd, resets a target (default working) to the first branch and merges the remaining branches, using Git’s octopus strategy by default. Source branches remain untouched and the target is explicitly documented as local and throw-away. This is ideal for “do these independently developed branches work together?” but says nothing about which branch depends on which or how to update them from trunk.

Popularity and maintenance

The canonical repository had 105 stars and 25 default-branch commits from 11 August 2025 through 11 August 2026. The repository’s latest commit was 11 July 2026. Mixer-facing docs and its agent skill changed in February and July 2026, showing live usage and policy maintenance, but the last executable mixer change was the slash-containing branch-name fix on 1 April 2020. There are no releases or tags, and the tool is one component in a personal configuration repository rather than a separately packaged product.

Licence

The scripts’ headers grant GPL version 3 or any later version, and the repository ships the GPLv3 text. This is OSI-approved free software, with strong copyleft obligations on distributed derivatives. This report is not legal advice.

Strengths and trade-offs

  • Strength: tiny, transparent, dependency-light, and uniquely supports arbitrary fan-in integration without rebasing or force-pushing source branches.
  • Strength: mix membership is easy for an agent to inspect and edit, and rebuilding the target is deterministic when merges are conflict-free.
  • Risk: git checkout -B destructively resets the target and cannot operate on a target already checked out in another worktree; the scripts do not enumerate or coordinate worktrees.
  • Risk: there is no dry-run option despite one being mentioned in repository guidance, no explicit clean-tree preflight, no remote fetch/push or merged-branch cleanup, and no structured output.
  • Risk: octopus conflicts abort the command; the sequential strategy opens an interactive shell and does not itself verify that conflict resolution was completed before proceeding.
  • Boundary: a mix branch should never become a PR or shared source of truth. It is a test artifact, not a stack.

worktrunk-sync

Verdict: the most natural first experiment for an existing Worktrunk user. It adds the missing repository-wide stack synchronization layer without replacing wt. Start with wt sync -nv, then local rebases; postpone --push and especially --prune until behavior is trusted. Its youth, one-maintainer footprint, and missing licence file prevent an unconditional adoption recommendation.

GitHub stars15 as of 11 August 2026 UTC
Maintenance41 commits since creation; latest meaningful fix and release 29 April 2026
LicenceMIT declared in package metadata; no governing licence file
Latest releasev0.1.2, 29 April 2026

Domain fit

The Rust binary runs as wt-sync or Worktrunk’s external wt sync subcommand. It enumerates branches attached to worktrees, requires the default branch to have a worktree, infers a dependency tree from merge bases, then rebases children in topological order inside each owning worktree. It persists a git-machete-compatible tree and per-branch fork points under .git/wt/, allowing safe rebase --onto after parent rewrites. It can fetch, force-push with lease, and prune integrated local/remote branches and worktrees. It cannot build a disposable aggregate of unrelated branches like ggmxd.

Popularity and maintenance

The repository was created on 10 April 2026, accumulated 41 commits and 15 stars, and released v0.1.2 on 29 April 2026. The latest meaningful change fixed stale branches in the stack file on 29 April. Three submitted pull requests were merged within roughly minutes to two days, but they were all from the maintainer; the only open issue, requesting push-only behavior, has been open since 3 July. The evidence supports “promising early project,” not mature maintenance.

Licence

The README says MIT and Cargo.toml declares license = "MIT", but the repository root contains no LICENSE or COPYING file. The intended licence is clear, but there is no governing licence text in the repository. That should be corrected before relying on it as cleanly licensed FOSS or redistributing it.

Strengths and trade-offs

  • Strength: minimal conceptual and operational overlap with Worktrunk; purpose-built around branches already isolated in worktrees.
  • Strength: preflights tracked changes and in-progress rebases across participating worktrees, stores successful fork points incrementally, exits non-zero on conflict, and offers dry-run/verbose planning.
  • Strength: automatic integration detection and child reparenting address the common “parent PR landed” transition.
  • Risk: topology inference is heuristic on the first run. Once written, the stack file becomes persistent metadata that needs review when inference is wrong.
  • Risk: --push force-pushes with lease and --prune can remove worktrees, local branches, and remote branches; these flags widen the blast radius sharply.
  • Risk: only branches with worktrees participate, unlike git-machete’s general branch layout.

git-machete

Verdict: the strongest mature comparator and the safest fallback if worktrunk-sync proves too young. Choose it when an explicit, editable branch tree and a guided repository-wide rebase/merge/push/pull traversal are desirable. It complements Worktrunk but is less tightly integrated with Worktrunk lifecycle operations.

GitHub stars1,132 as of 11 August 2026 UTC
Maintenance287 commits in the 12-month window; meaningful worktree fix 5 August 2026
LicenceMIT
Latest releasev3.44.1, 7 July 2026

Domain fit

git-machete records a forest of parent/child branches in an editable layout file, discovers likely topology, visualizes sync state, and traverses branches to rebase or merge them against parents and synchronize remotes. GitHub and GitLab commands can create and retarget stacked PRs/MRs. Current worktree support is explicit: a shared top-level machete file is the default, traversal enters the worktree that owns a branch, and an optional mode creates temporary worktrees so existing checkouts are not changed. It does not manage Worktrunk creation/removal and does not represent arbitrary many-to-one test mixes.

Popularity and maintenance

The canonical repository had 1,132 stars, 287 commits during the common window, and release v3.44.1 on 7 July 2026. The latest default-branch commit on 9 August was automated dependency maintenance; the latest meaningful commit on 5 August fixed worktree labeling. A concentrated series of worktree issues—including traversal, slide-out, layout consistency, and worktree navigation—was closed between January and July 2026, with tests dedicated to those paths. That combination supports an active, responsive classification.

Licence

The repository contains an MIT licence. It is permissive, OSI-approved free software with attribution and licence-notice obligations.

Strengths and trade-offs

  • Strength: years of adoption, broad packaging, rich status/navigation, explicit topology corrections, remote synchronization, and forge integration.
  • Strength: the clearest current worktree semantics among mature contenders, including temporary-worktree traversal and shared/per-worktree layout control.
  • Strength: ships an upstream agent skill and non-interactive --yes/--no-interactive-rebase controls.
  • Trade-off: more metadata and workflow surface than worktrunk-sync; agents must understand layout annotations, qualifiers, fork-point behavior, and push policy.
  • Trade-off: traversal can change directories and checked-out branches unless configured for temporary worktrees, and defaults can push branches.
  • Boundary: it manages dependency trees and stacked PRs, not disposable independent-branch integration builds.

git-branchless

Verdict: consider for advanced commit-DAG visualization, undo, in-memory restacking, or speculative merge checks—not as the default coordinator for many Worktrunk worktrees. Its explicit alpha status and unresolved cross-worktree correctness reports are material.

Maintenance107 commits in the 12-month window; latest meaningful fix 15 July 2026
LicenceMIT OR Apache-2.0
Latest releasev0.11.1, 21 May 2026

Domain fit

git-branchless works one abstraction level below most candidates: it records and manipulates the commit DAG, supports anonymous branches, visualizes stacks, performs in-memory moves/restacks, syncs local stacks without checking each one out, and can calculate speculative merges to expose conflicts. This is powerful for parallel divergent development, but it does not own Worktrunk lifecycle or provide the explicit worktree ownership model required for coordinating many agents.

Popularity and maintenance

The canonical repository led the shortlist with 4,110 stars, recorded 107 commits during the common window, released v0.11.1 on 21 May 2026, and last received a meaningful fix on 15 July. The project nevertheless labels itself alpha and warns that workflows and on-disk formats may change. Open issues include moving branches sensibly across worktrees, initialization with non-standard worktree layouts, and git branchless sync staging changes in other worktrees.

Licence

The project is dual-licensed under MIT or Apache-2.0, with both governing licence texts present. Both are permissive, OSI-approved free software licences; users may select either licence under the project’s terms.

Strengths and trade-offs

  • Strength: sophisticated DAG manipulation, fast in-memory rebases, strong undo, smartlog, divergent workflows, and speculative conflict detection.
  • Strength: many operations avoid checking out branches, which can preserve expensive build state in a single working copy.
  • Risk: hooks and repository-wide metadata introduce a deeper Git behavioral layer than the other candidates.
  • Risk: explicit alpha status plus open cross-worktree issues make it a poor baseline safety policy for parallel agents.
  • Boundary: speculative merges overlap part of ggmxd’s testing intent, but they do not maintain a persistent runnable aggregate worktree.

Domain fit

Stackit explicitly combines branch-tree tracking, restacking, GitHub PR submission and merging, undo snapshots, machine-readable state, agent skills, and managed worktrees. Hidden anchor branches separate worktree ownership; content-changing commands must run in the owning worktree, while sync/restack can reconcile the repository globally. Methodology and shortlist

The domain is repository-local coordination of multiple concurrent branches and linked worktrees, especially when coding agents produce parallel short- or long-lived changes. The user supplied ggmx/ggmxd, worktrunk-sync, and git-machete. Git Town and git-branchless were added as the most established broad FOSS alternatives; Stackit was added because it directly combines stacked branches, managed worktrees, and agent integration. StGit was excluded because its patch-series model is less directly aligned with branch-per-worktree agent streams; gh-stack and git-stk were excluded as narrower or less-established forge/stack tools; Graphite was excluded because the relevant product is not a clean self-hosted FOSS comparator.

GitHub stars, default-branch commits from 11 August 2025 through 11 August 2026, latest meaningful commit, latest stable GitHub release, archival state, repository licence files, primary documentation, source where needed, and relevant worktree issues were observed on 11 August 2026 UTC. Commit counts come from the GitHub commits API for the canonical default branch. Stars measure attention, not quality; high commit velocity can indicate churn rather than maturity; issue searches are evidence, not proof that no other defect exists. The local mixer was additionally inspected from its current source and agent skill.

Comparative recommendation

  1. Do not replace ggmx/ggmxd on category error. Keep the mixer for local, throw-away, arbitrary branch integration tests. None of the stack managers has the same fan-in model.
  2. Trial worktrunk-sync first as the smallest extension to the current Worktrunk workflow. Begin with wt sync -nv and local-only rebases in a disposable repository fixture. Review the inferred tree. Do not enable --push or --prune by default. Ask upstream to add an MIT licence file before treating redistribution terms as settled.
  3. Use git-machete as the mature benchmark and fallback. It is preferable when topology should be explicit, non-worktree branches must participate, and GitHub/GitLab PR chains matter. Configure temporary-worktree traversal if preserving every existing checkout is important.
  4. Watch rather than standardize on Stackit. Its integrated worktree ownership and agent interfaces are compelling, but adopting it now would duplicate Worktrunk and accept substantial pre-1.0 churn.
  5. Do not select Git Town or git-branchless as the default multi-worktree policy today. Both are strong projects, but their open worktree issues cut across the safety properties needed for parallel agents.

The resulting policy can therefore separate concerns cleanly: Worktrunk creates and locates isolated worktrees; worktrunk-sync or git-machete maintains dependency ancestry; normal Git branches and atomic commits remain publication units; and ggmxd produces an unpublished integration branch only when independent streams need combined testing.

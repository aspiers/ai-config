Focused FOSS comparison

Managing a fleet of active, interdependent Git branches

A deeper comparison of tools that know about a set of related branches or changes and can maintain that set: discovering or recording dependencies, rebasing in dependency order, landing reviewed work, pruning integrated state, and recovering when a fleet-wide operation goes wrong.

Evidence observed 25 August 2026 UTC · 11 detailed candidates · activity window 25 August 2025–25 August 2026

⚠️ Architecture-specific recommendation. Capability evidence is general, but the final architecture is evaluated against the target Worktrunk, Herdr, AgentBox and branch-mixer workflow. Other readers should substitute their own worktree, forge, sandbox and control-plane constraints.

Bottom line

Pick the branch authority by operating model, not by feature count

Git Machete remains the best modular topology authority for a Worktrunk-based cockpit: its explicit, reviewable forest deliberately follows branches into their owning worktrees. Independent clones need an explicit topology-distribution or regeneration step because .git/machete is clone-local state. Git Town is the best routine branch-fleet operator when dry-run, safe pruning, persisted run state and undo matter more than bulk stacked-PR landing. git-spice is the best publication engine, but it cannot deliver repository-wide restacking when active branches are all pinned in separate worktrees: it skips the checked-out branch and its entire upstack.

For a single integrated replacement, Stax is the best current pilot. Stackit has the most ambitious remote metadata and automation design, but an open topology-corruption issue keeps it in the lab. Jujutsu is the strongest strategic model replacement; it should be evaluated as the repository owner, not inserted as another Git helper.

ggmx/ggmxd remain outside this contest. They build a disposable fan-in target from otherwise independent tips; they neither record branch dependency intent nor restack, land or prune the source branches. That makes them complementary to every qualifying tool here, not an overlapping branch manager.

What counts as a branch-fleet manager?

1 · Know the setRecord or infer which active lines of work exist and how they depend on one another.
2 · Reconcile upstreamFetch or update trunk, then restack parents before descendants without duplicating commits.
3 · RecoverPreview risky changes, persist interrupted state, continue or abort conflicts, and restore refs after mistakes.
4 · Publish or landPush with lease safety, retarget reviews, and merge dependency stacks in a valid order.
5 · Retire stateDetect integrated or remote-gone work, reparent survivors, and prune branches or worktrees without losing unique files.

A worktree launcher is useful but does not qualify unless it also owns branch relationships. A stacked-PR client qualifies only if it maintains local lineage, not merely remote review metadata. VCS alternatives are included in a clearly marked category because they solve the same fleet problem with changes/bookmarks instead of conventional Git branches.

Git Machete

Verdict: The clearest modular topology authority. Its explicit, human-readable forest and mature whole-layout traversal fit a cockpit in which Worktrunk owns persistent worktrees. Independent agent clones need deliberate topology distribution or their own reviewed discovery.

Popularity1,135 stars
Maintenance284 commits; meaningful worktree fix 5 August 2026; v3.44.1 on 7 July
LicenceMIT

Topology and mass maintenance

An indented .git/machete file is the authoritative forest. That explicit intent distinguishes “these branches happen to share ancestry” from “this review depends on that review.” discover uses reflog heuristics to propose a recency-filtered layout—roughly ten branches by default unless the cutoff is overridden—preserves the old file, and leaves the proposal open to review. The file lives under .git, so it is not transferred by clone. traverse --whole then processes the declared layout parents-first and can fetch, rebase or merge, reconcile tracking counterparts, push, slide merged nodes out, and create or retarget GitHub PRs and GitLab MRs.

Worktrees, landing and recovery

Traversal changes into the existing worktree that owns a branch, or can create a temporary worktree for a branch checked out nowhere. That is the strongest clean composition with Worktrunk in this field. The trade-off is recovery: traversal is stateless. Resolve or abort the native Git rebase/merge and rerun from the current branch. There is no general transaction rollback or true dry-run. advance can fast-forward one green child into its parent, push the parent and remove the child from the layout, but it is not an automated whole-stack forge landing queue.

Current-release caveat: a worktree-dependent discover discrepancy was fixed quickly on develop, but the fix was not in v3.44.1 at the observation date. Use an explicitly reviewed layout or wait for the fix release.

Evidence

  • Layout file, discovery and whole-layout traversal
  • Advance semantics
  • Worktree discovery issue and merged fix
  • Latest observed stable release

Git Town

Verdict: The strongest routine manager for a heterogeneous fleet of branches. It combines hierarchy, branch-type policy, whole-repository synchronization, guarded cleanup, broad dry-run support, persisted command state and repository-level undo.

Popularity3,365 stars
Maintenance620 commits; active product work in July 2026; v24.0.0 on 23 July
LicenceMIT

Topology and policy-driven sync

Parent links live in Git configuration as git-town-branch.<branch>.parent, while branch types distinguish feature, prototype, contribution and perennial lines of work. sync --all applies those policies to every local branch in lineage order; --stack narrows the scope. Rebase, merge and compress strategies can differ by workflow. Unknown parents can be inferred from an open PR or supplied interactively, although there is no Machete-style proposed whole-forest discovery.

Safety, worktrees and landing

Current features exercise synchronization and conflict recovery from linked worktrees, and the tool does not try to provision those worktrees itself. Commands can persist a plan, continue, skip or undo; the immutable runlog records local and remote branch SHAs before and after operations. Dry-run is broad, and walk can execute an arbitrary command across a stack or all branches. Cleanup is conservative: remote-gone branches are deleted only after proving they contain no unshipped work, and --prune removes empty branches.

The main gap is stack landing. ship acts on one branch, normally a direct child of main. A stack is shipped oldest-first with repeated commands; there is no ship --stack. Also treat unqualified delete on the current branch carefully because its documented scope includes uncommitted changes.

  • Linked-worktree conflict scenario

git-spice

Verdict: The most capable FOSS stacked-review and bottom-up landing engine, with broad forge support and good structured output. Its repository-wide restack promise breaks down in a branch-per-worktree fleet.

Popularity750 stars
Maintenance461 commits; meaningful GitHub stack-gateway work 24 August 2026; v0.31.2 on 21 July
LicenceGPL-3.0-or-later

Topology, sync and publication

Versioned JSON objects under refs/spice/data record each branch’s base name and base hash. repo restack rebases every tracked branch in dependency order, with stack/upstack/downstack scopes for smaller operations. repo sync --restack updates trunk, deletes merged review branches, retargets surviving reviews, and optionally restacks them. GitHub, GitLab, Bitbucket, Gitea, Forgejo and Codeberg are supported, including separate upstream and push remotes.

Experimental branch merge, downstack merge and stack merge land through forge APIs, wait for readiness, then restack and resubmit survivors. Multiple independent starting branches are accepted. No other modular Git-native candidate combines this breadth of forge support with automated bottom-up landing.

Fork mode has an important publication limit: submission creates review requests only for branches based directly on trunk. Dependent branches are pushed to the fork but receive no review request until their bases land and they are restacked onto trunk. Separate upstream/push remotes therefore do not preserve the normal stacked-review experience.

The decisive worktree limitation

git-spice reports linked-worktree paths but does not run a planned rebase in the branch’s owning worktree. If a branch is checked out in another worktree, restack skips that branch and every descendant above it. That is a sensible protection against moving a checked-out ref, but it defeats whole-repository restacking when Worktrunk keeps every active branch materialized. Use git-spice where branches are usually not pinned to separate worktrees, or design an explicit quiesce/dematerialize step before fleet mutation.

Interrupted rebases have persistent continue/abort state. JSON Lines output exposes topology, worktree, review and push state; dry-run coverage is command-specific and there is no general completed-operation undo.

Stax

Verdict: The best immediate all-in-one pilot. It owns topology, branch-aware worktrees, parallel agent lanes, bulk refresh, stack landing, cleanup, recovery, TUI and web interaction—but should replace Worktrunk’s ownership rather than compete with it.

Popularity123 stars; repository created December 2025
Maintenance1,111 commits and 164 releases; v0.105.1 on 23 August 2026
LicenceMIT

Branch-fleet depth

Per-branch JSON blobs under refs/branch-metadata/* record parents, revisions, remote and review state. The model supports forked trees and multiple independent stacks. validate detects cycles, orphans and stale metadata; fix --dry-run can repair it. refresh --all-stacks updates trunk once, then restacks and submits every stack. Current-stack, selected-upstack and managed-worktree restack scopes are also available, while run --parallel executes checks in temporary worktrees.

Local cascaded merge, one-tip stack landing, GitHub merge queues and GitLab merge trains are supported. With GitHub native stacks, Stax can delegate atomic landing to gh-stack. sync and the read-only-by-default sweep conservatively identify merged, empty or upstream-gone branches, reparent children and transact the ref changes. Manual middle-branch branch delete is a sharp edge: it deliberately leaves descendants pointing at the deleted parent, so use sync/detach or explicit reparenting.

Recovery and cockpit ownership

Branch snapshots and operation receipts support undo and redo. Continue, abort and rerere cover interrupted conflicts. The transaction restores refs, metadata and deleted branches, but not a removed worktree directory or forge-side PR-base edits. Worktree cleanup skips dirty/conflicted/active lanes unless forced; warm-slot reuse can run git clean -fd, so ordinary untracked files are outside the undo boundary.

Bare st opens a topology-and-review TUI. Current main also has a token-protected localhost web workspace, newer than the latest release. Agent workflows cover Codex, Claude, Gemini, OpenCode and Pi. This is an integrated cockpit owner, not a harmless extra CLI above Worktrunk.

  • Merge and cascade, sweep and undo/redo
  • Worktrees, TUI and current web workspace
  • Latest observed stable release

Stackit

Verdict: The architecture leader for remotely synchronized metadata, parallel multi-stack maintenance, structured automation and multi-stack consolidation. Keep it in a disposable lab until its current partial-cleanup topology bug is fixed and destructive paths are verified.

Popularity32 stars; repository created December 2025
Maintenance2,620 commits and 75 releases; v0.26.1 on 17 August 2026
LicenceMIT

Remote topology and mass operations

Stackit stores remotely synchronized branch and stack metadata under dedicated Git ref namespaces, with separate local-only and fetched remote state. Parents, revisions, review links, stack IDs and merged-downstack history travel without a proprietary metadata server. Trees are normal; an optional linear mode forbids forks below non-trunk branches.

restack --all-stacks --parallel groups independent stacks and preflights them in temporary worktrees. A conflict or dirty checked-out branch holds back that entire dependency group while unrelated groups proceed. In JSON mode, expected conflicts are structured results and can exit zero, so automation must inspect status, conflicts, blocked and held. Merge drain lands bottom-up; merge ship builds a consolidation branch and can combine multiple independent stacks into one tested PR.

Worktree and safety boundary

A managed worktree owns a whole stack through a hidden anchor branch. Stackit checks actual linked checkouts before moving refs and can hold back dirty owners. It is therefore another worktree ownership plane, not a clean co-owner beside Worktrunk. Snapshots protect branch SHAs and metadata refs, not uncommitted files. Auto-clean is enabled by default, and ignored warm-start files copied via .worktreeinclude can be permanently deleted by remove, detach or prune.

Production blocker: open issue #1656 reports sync reparenting a child before discovering that its checked-out parent cannot be deleted, leaving invalid topology in linear mode. This is exactly the kind of partial fleet mutation the control plane must prevent.

  • Multi-stack shipping, worktree ownership and undo snapshots
  • Resolved dirty-worktree data-loss report and open topology issue
  • Latest observed stable release

git-stack

Verdict: A compact and thoughtfully safe inferred-graph engine for synchronizing local branch stacks. Its functional development has gone quiet, it lacks forge landing, and conflict recovery drops the user into raw Git.

Popularity649 stars
Maintenance88 commits in the window, all dependency/CI automation; latest package version 0.10.20 on 5 August 2025
LicenceMIT OR Apache-2.0

Inferred fleet and safety model

git-stack derives stack structure from the commit graph and protected-branch configuration rather than recording intended parent links. git sync updates protected bases, rebases development branches in dependency order, fetches the push remote, prunes deleted tracking refs and can remove branches already integrated upstream. git stack --rebase and graph scopes cover the current tree, descendants or all stacks; amend/reword operations automatically carry descendants forward.

Its mutation design is conservative: permanent ref changes are deferred until the planned operation completes, a dry-run is available, and branches are implicitly backed up in the format used by git-branch-stash. The major gap is interactive failure handling. When a rebase conflicts, git-stack gives up and instructs the user to use native git rebase; there is no integrated continue/abort journal. There is also no PR creation, retargeting or landing engine. The README recommends a conservative one-PR-at-a-time review workflow.

The project still receives automated dependency maintenance, but the latest functional package work sits just outside the common one-year window and GitHub Releases lag the package changelog. Treat it as maintained infrastructure with quiet product development, not an actively expanding control plane.

worktrunk-sync

Verdict: The smallest native companion to a branch-per-Worktrunk-worktree workflow. Its durable fork points and parent-first rebase plan are promising; tiny adoption, weak licence hygiene and unsafe partial-success signaling keep it a controlled pilot.

Popularity16 stars
Maintenance41 lifetime commits; v0.1.2 and latest activity 29 April 2026
LicenceMIT declared; governing licence file absent

Worktree-derived topology

The first run compares merge bases among non-detached branches that have worktrees. It stores the resulting topology in .git/wt/stack and fork points in .git/wt/stack-forkpoints; that saved state then becomes authoritative. This matters because a parent rewrite destroys some of the ancestry evidence used by initial inference. Ties are warned about but not presented for confirmation, and branches without worktrees are invisible. The default branch must also have a worktree.

wt sync operates on one stack or every worktree branch with --all, always rebasing parents before children. Options add fetch, lease-protected push and pruning of integrated worktrees/branches. Conflicts stop at the first failing rebase; use native git rebase --continue or --abort, then rerun. Completed fork points act as checkpoints, but there is no tool-level undo or command journal.

Automation blocker: prune can remove the worktree, local branch, upstream remote branch and Worktrunk staged-trash content. Some push, prune and remote-delete failures are printed without making the overall command fail. Do not enable unattended destructive automation until exit semantics are fixed and verified.

GitHub gh-stack

Verdict: An important GitHub-native linear-stack baseline with unusually good interactive reordering and atomic remote landing. The defining Stack service is proprietary, local commands do not manage a linked-worktree fleet, and publication can partially succeed.

Popularity1,363 stars; repository created February 2026
Maintenance92 lifetime commits; active through 24 August; v0.1.0 on 29 July 2026
LicenceMIT client; GitHub stack APIs remain proprietary

Linear stack workflow

Local JSON metadata records an ordered list of branches while GitHub stores the corresponding remote Stack object. gh stack rebase fetches and cascades bottom-up; merged PRs are rebased onto the landed commit, and users can scope upstack or downstack. modify previews dropping, folding, inserting, renaming and reordering before applying a snapshot-backed rewrite. sync reconciles local branches, remote refs, PRs and Stack state and can optionally prune.

Rebase has strong all-branch abort semantics: a snapshot restores the full stack after conflict or cancellation. Synchronization intentionally refuses to leave a partially rebased stack. Publication is weaker: push and submit operate branch-by-branch, so a lease rejection or API failure can leave earlier branches already updated. Noninteractive divergence can also exit successfully without changing anything, which automation must detect from output/state rather than status alone.

Boundary and worktrees

gh stack merge gives atomic server-side landing, but only through GitHub’s proprietary Stacked PRs service. The client can link remotely managed branches from Jujutsu, Sapling, Git Town or separate worktrees, but that mode is an API bridge with no local navigation or branch-fleet lifecycle. Normal local commands assume branches can be checked out and are not a Worktrunk-aware mass-restack solution.

git-branchless

Verdict: The strongest Git-native commit-DAG maintenance and undo specialist. It can synchronize every draft stack onto one main branch and repair descendants after rewrites, but it remains alpha and does not provide a dependable stack-landing control plane.

Popularity4,115 stars
Maintenance107 commits; meaningful work 15 July 2026; v0.11.1 on 21 May
LicenceMIT OR Apache-2.0

Repository-wide inferred graph

Smartlog shows visible draft stacks in one commit DAG. git sync --pull fetches remotes, updates the configured main branch, discovers draft roots and moves all stacks onto it; revsets can restrict the set. git restack finds children abandoned by amend/rebase operations and moves their subtrees to the rewritten commits. The model is ancestry-derived rather than a manifest of intended review dependencies, and every stack ultimately targets one configured main.

Upstream-equivalent changes are deduplicated. git hide can retire selected commits or entire descendant sets and delete their branch pointers; the event log and git undo restore the previous graph and refs. In-memory conflicts abort cleanly, with an optional retry through on-disk native Git rebase. Merge-shaped DAGs remain an edge case.

Cockpit composition

Linked worktrees are recognized and tested for display and movement, but git-branchless does not create, clean or retire them. Its stable raw OID query form and revsets support scripting without a JSON-first state contract. git submit has branch, GitHub and Phabricator providers, but the GitHub option describes itself as likely buggy and there is no landing queue. Use it as an expert graph/undo engine, with real trials around branches checked out in other Worktrunk worktrees.

Jujutsu

Verdict: The strongest strategic answer to dependency-DAG maintenance, bulk rewriting, persistent conflicts and recovery. It replaces Git’s branch/worktree mental model rather than serving as a branch-manager layer.

Popularity31,185 stars
Maintenance1,928 commits; active 25 August 2026; v0.44.0 on 6 August
LicenceApache-2.0

Native change fleet

The change DAG itself is the dependency model, and bookmarks are movable labels rather than checked-out branch identities. One jj rebase transaction can move multiple branches, selected revision subtrees or arbitrary sources while preserving dependency edges. Descendants automatically follow rewritten changes. Conflicts are first-class commit state, so a large rewrite completes with conflicted changes recorded in the graph; resolve them later instead of driving a continue/abort loop.

jj abandon removes revisions and rebases descendants. The operation log, undo, redo and operation restore cover complete repository state and make recovery the best in this comparison. Native workspaces share one repository, while revsets, templates and JSON serialization provide a powerful automation surface.

Why it is not the default cockpit layer

There is no single policy command to fetch and rebase every outstanding line: the official GitHub flow fetches, then names the branches or revisions to rebase. Publication is bookmark-based safe Git push; PR creation, dependency status and landing remain external. More importantly, Jujutsu workspaces replace Git worktrees. Additional workspaces in a colocated repository are not yet recognizable as Git worktrees, limiting composition with Worktrunk and Git-dependent agent tooling. Evaluate one representative repository end-to-end instead of mixing authorities.

Stack workflow

Smartlog presents the draft DAG and bookmarks label points in it. sl rebase can move a commit, a source plus descendants, a whole branch-relative set, or multiple revision/destination pairs. sl restack repairs orphaned descendants after amend/absorb-style rewrites. These operations target the current stack or selected revisions; there is no native all-outstanding-stacks synchronization policy.

Conventional rebase state supports continue, abort and quit. sl hide --cleanup retires obsolete stacks and unnecessary remote bookmarks while leaving hidden commits recoverable. Undo, redo and journal provide strong local recovery, although they do not reverse remote bookmark changes. sl pr submit --stack creates or updates one GitHub PR per commit; smartlog and the browser UI can show review state.

Missing fleet pieces

Sapling has no documented parallel worktree/workspace facility, and the explicit parallel-agent request remains open. Stack submission does not land the stack; an open issue documents the manual land, pull, rebase and resubmit loop. GitHub PRs overlap from main and are best reviewed through ReviewStack rather than native GitHub stacked-PR semantics. This is a coherent alternate VCS/review workflow, not a modular branch authority for the existing Worktrunk cockpit.

Methodology, scope and near misses

Research first queried the local AgentsView session index and reused the earlier Git Machete, worktrunk-sync, cockpit-layer and branch-mixer evidence instead of recreating it. Independent passes then refreshed current canonical documentation, source, release and repository metadata for mature modular tools, young integrated managers, and change-DAG alternatives. Activity was measured on each canonical default branch over the same dates; volatile capability claims were checked against current primary sources rather than search snippets.

Why several relevant projects are not scored peers

  • Worktrunk, git-stint and T3 Code make branch worktrees or agent sessions easy to create and use, but do not own a dependency graph or perform parent-first fleet maintenance. They are workspace/cockpit layers.
  • ggmx/ggmxd maintain a named fan-in target from arbitrary peer tips. That is integration composition, not dependency topology, and remains a separate layer after the topology authority finishes rewriting sources.
  • StGit is a mature GPL-2.0 patch-series manager with linked-worktree support, undo and repair, but each mutating command operates on one branch’s patch stack. It cannot discover and maintain a repository full of dependent branches.
  • spr is centered on a commit stack carried on one local branch and GitHub review publication, rather than many active branch identities.
  • ez-stack is the most relevant watch candidate: an MIT agent-oriented stack/worktree manager with sync, merge, receipts and leases. At 23 stars and only six months old, independent operational evidence is too thin for the primary recommendation.
  • GitButler remains Fair Source rather than currently OSI-compatible FOSS. Graphite requires a proprietary account/service for its defining workflow. They fall outside the requested FOSS boundary.

Interpretive limits

Repository issue reports identify plausible current risk; they are not claims that every defect was independently reproduced. Commit volume in Stax, Stackit and Sapling includes concentrated maintainer, bot or monorepo activity and is not a maturity score. GitHub gh-stack’s local client is FOSS, but its atomic landing capability depends on a proprietary service, so the report does not call the complete solution FOSS.

Recommended architecture and test plan

  1. Default modular lane: keep Worktrunk as worktree lifecycle owner and Git Machete as the sole explicit topology authority. Use a reviewed .git/machete forest, explicitly distribute or regenerate it for independent clones, disable default push during traversal, and let traversal follow existing Worktrunk paths or use temporary worktrees.
  2. Safety-first challenger: pilot Git Town against the same representative repository. Exercise sync --all, dry-run, runlog, undo, linked-worktree conflicts, remote-gone branches, empty-branch pruning and repeated oldest-first shipping.
  3. Publication challenger: pilot git-spice in a clone where only the current branch has a worktree. Measure repo-wide restack, JSON integration, bottom-up stack merge and recovery. Test fork mode separately and confirm that only trunk-based branches receive review requests. Prove the checked-out-branch/upstack skip before considering it for a Worktrunk fleet.
  4. Integrated lane: pilot Stax instead of Worktrunk, not on top of it. Test all-stack refresh, worktree lanes, sweep, manual middle-branch deletion, warm-slot untracked-file behavior, undo/redo and forge-side effects that undo cannot reverse.
  5. Laboratory lane: use Stackit as an automation and metadata reference only until issue #1656 is fixed. Disable auto-clean, seed dirty and ignored files, force partial failure, and verify JSON callers inspect structured conflict status rather than exit code alone.
  6. Strategic lane: trial Jujutsu on a complete representative repository and toolchain. Treat native workspaces, bookmarks, hooks, forge reviews and Worktrunk replacement as one adoption decision.
  7. Keep fan-in isolated: run ggmxd only after the branch authority is idle and source refs are stable. Keep the mix target unpublished and out of every stack topology.

Acceptance tests

  • Model two independent stacks, one forked stack, one long-lived release branch and one unrelated fan-in mix; prove the manager distinguishes dependency from mere ancestry.
  • Rewrite both a root and a middle parent, then run one fleet operation. Verify parent-first ordering, review retargeting and no duplicated commits.
  • Keep one affected branch dirty in another worktree, one remote branch deleted and one review already merged. Record what is blocked, skipped, changed and pruned.
  • Interrupt a rebase mid-stack, recover, then undo a completed but incorrect fleet operation. Audit branch refs, worktree files, metadata refs and forge state separately.
  • Land one linear stack and prune it; verify unique local commits, ordinary untracked files, ignored secrets and remote refs are either preserved or deliberately handled.
  • Require machine-readable plans to distinguish clean success, partial success, expected conflict, skipped work and destructive work—not merely process exit zero.

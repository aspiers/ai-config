Recommended starting point

Remote Docker + an independent recovery layer

Start on a VPS you control when agents spend substantial time actively running. AgentBox can freeze a box exactly with docker pause, or stop it while preserving the writable filesystem. The fixed VPS bill is usually attractive once active hours accumulate.

But treat the VPS as one failure domain. The live container and AgentBox’s docker commit checkpoint remain on the same Docker host. Add automatic branch export or push plus off-host backups before trusting it with irreplaceable work.

Managed shortlist

Trial Daytona and E2B side by side

Both preserve filesystem, memory and running processes without reserving your VPS RAM while paused. Daytona’s lifecycle defaults are especially friendly to long dormancy; E2B’s paused sandboxes are documented as indefinite and its snapshots survive deletion of the source sandbox.

For a UK user, benchmark Daytona’s AgentBox VM route in US-East. For E2B, decide whether the 1-hour Hobby limit is workable or whether the 24-hour Pro limit justifies the $150 monthly base fee.

The key analytical distinction

“Persistent” is not one property

There are five layers. A provider can be excellent at exact resume and poor at disaster recovery, or vice versa. A paused VM is not a backup.

1 · Live executionThe process keeps running after you detach.
Example: tmux on an always-on VPS.
2 · Memory suspendThe process returns at the exact instruction.
Example: E2B or Daytona VM pause.
3 · Filesystem persistenceDirty files survive, even if processes restart.
Example: Vercel persistent sandbox.
4 · Independent snapshotA deleted box can be reconstructed.
Example: E2B or Daytona snapshot.
5 · Off-provider backupHost, account or provider failure does not erase work.
Example: pushed branch plus object storage.
Your non-negotiable requirement belongs at layer 5. Layers 1–4 improve convenience and resilience; none alone guarantees recovery from provider deletion, account loss, host failure or operator error.

Economics

Long active runs favour a fixed VPS; many dormant boxes favour real suspend

Daytona, E2B and Tenki publish essentially the same compute unit rates as observed on 17 August 2026: $0.0504 per vCPU-hour and $0.0162 per GiB-hour. A 2-vCPU / 4-GiB sandbox therefore costs about $0.1656 per active hour, before storage. That is roughly $16.56 for 100 active hours or $120.89 for 730 active hours. E2B Pro adds $150/month.

Remote Docker instead turns cost into a fixed-capacity problem: you pay for the VPS whether the agent is busy or idle, but multiple boxes share it. A Docker-paused box uses no CPU yet retains mapped RAM. Daytona/E2B can externalise suspended memory and stop billing CPU/RAM, which becomes compelling when the dormant-to-active ratio is high.

AgentBox’s documented default pet-VM examples are approximately €4/month per Hetzner box and $24/month per DigitalOcean box. These can be sensible for a handful of permanent boxes, but a shared Remote Docker VPS normally amortises better across a fleet.

Prices are volatile and exclude taxes, bandwidth, snapshots and storage. Recheck before purchase. Sources: Daytona pricing, E2B pricing, Tenki pricing, AgentBox Hetzner, AgentBox DigitalOcean.

Remote Docker on your own VPS

Verdict and best fit: Tier A The best starting point when active compute is substantial, you are comfortable operating a VPS, and container isolation is sufficient. Add off-host recovery before calling it safe.

GitHub stars353 for madarco/agentbox
Observed 17 Aug 2026 UTC
MaintenanceActive; repository pushed 3 Aug 2026 and docs observed at v0.27.2
LicenceMIT for AgentBox; your VPS/Docker terms also apply

Domain fit

AgentBox connects over SSH to a Docker engine you control. Each box is a separate container; several boxes share the same host. agentbox pause maps to docker pause, so every process freezes and resumes nearly instantly. agentbox stop frees RAM and kills the process tree while keeping the container’s writable filesystem.

Persistence and failure boundary

Docker documents pause as the Linux freezer cgroup. That preserves process state only while the host and its memory survive. A host reboot loses the exact in-memory session. AgentBox checkpoints use docker commit and remain on the engine that created them, so the live box and checkpoint share one failure domain.

Design consequence: use pause for short/medium gaps; use stop for long dormancy; use an off-host Git/bundle/object-storage job for actual recovery. A provider snapshot of the VPS is useful, but it is still not independent of the provider account.

Strengths and trade-offs

  • Strong economics for long-running agents and many boxes on one host.
  • No provider-imposed wall-clock TTL or continuous-session cap.
  • Full operational control and predictable geography.
  • Paused boxes retain RAM; host failure or reboot destroys exact process state.
  • Shared-kernel containers are a weaker isolation boundary than separate microVMs for adversarial code.

Daytona Linux VM

Verdict and best fit: Tier A Arguably the strongest managed option for long-idle AgentBox sessions: memory and filesystem survive pause, paused state is retained until deletion by default, and paused compute releases CPU/RAM billing.

GitHub stars71,980 for the former daytonaio/daytona core
Historical attention, not a current openness signal
MaintenanceHosted service and SDKs active; former monorepo’s last push 24 Jul 2026
LicenceHosted service is proprietary; Daytona announced closure of its former open core

Domain fit

AgentBox defaults Daytona boxes to linux-vm. After 25 minutes of genuine agent inactivity, the host pauses the VM. Daytona’s pause preserves filesystem, memory and running processes; stopped, paused and archived sandboxes remain until explicit deletion unless you configure auto-delete or a wall-clock TTL.

Daytona also offers cold and hot snapshots, forks, and S3-backed volumes that can outlive a sandbox. In the current AgentBox mapping, a checkpoint stops the box to snapshot it, so the checkpoint workflow preserves disk but kills that live process instance. Daytona’s own platform has richer hot-snapshot capability than AgentBox currently exposes.

Geography and integration caveats

AgentBox’s current provider page says the Linux VM class is pinned to US-East; its container class can use EU regions but does not retain process memory on pause. Daytona’s broader region documentation lists shared US and EU targets, so this restriction should be treated as an AgentBox/class constraint and tested against the exact build you deploy.

AgentBox also notes that Daytona VM sandboxes ignore mounted Daytona volumes. The practical stack is therefore: VM pause for exact resume + AgentBox/Daytona snapshot for disk recovery + Git/off-provider backup for real durability.

Strengths and trade-offs

  • Explicit default retention: no auto-delete or wall-clock TTL unless configured.
  • Paused VM retains memory but bills reserved disk only.
  • No E2B-style 1-hour Hobby continuous-runtime cap documented.
  • US-East latency is the central concern for an interactive UK workflow.
  • AgentBox does not expose every native Daytona persistence primitive.

E2B

Verdict and best fit: Tier A Current E2B is a much stronger persistence fit than the older destructive-timeout experience suggests. Choose it when full-state suspend and managed microVM isolation outweigh the plan limits and Pro fee.

GitHub stars13,436 for e2b-dev/E2B
Observed 17 Aug 2026 UTC
MaintenanceActive; pushed 17 Aug 2026; latest release Python SDK 2.39.1 on 13 Aug
LicenceApache-2.0 core + hosted-service terms

Domain fit

E2B documents pause as preservation of both filesystem and memory, including running processes and loaded state. Paused sandboxes are kept indefinitely with no automatic TTL. Explicit snapshots capture filesystem and memory, can create new sandboxes, and survive deletion of the source sandbox.

Why earlier work may have disappeared

E2B’s timeout is only safe if its lifecycle action is configured to pause. The SDK documentation shows lifecycle configuration such as onTimeout: 'pause'; killing a sandbox is permanent. A plausible explanation for earlier loss is raw/default or older integration behaviour that reached a destructive timeout rather than the present full pause. That is an inference, not a retrospective diagnosis.

Limits and documentation lag

The continuous-runtime ceiling is the material constraint: one hour on Hobby and 24 hours on Pro, reset after a pause/resume cycle. Pro costs $150/month plus usage. AgentBox’s provider page still labels E2B support “Nightly,” and parts of the wider AgentBox documentation lag newer E2B functionality. Run a destructive-lifecycle test against the exact version before entrusting it with work.

Required acceptance test: create a dirty repository and an in-memory marker process, allow the AgentBox timeout to fire, resume after 24 hours, verify both markers, then snapshot, delete the source box, and restore from the snapshot.

Tenki Sandbox

Verdict and best fit: Tier B Architecturally attractive and cost-competitive, but still too new to trust without verifying the community AgentBox provider’s effective retention defaults.

GitHub stars0 for the young Go SDK
Observed 17 Aug 2026 UTC; stars are not meaningful at this age
MaintenanceNew and active; SDK pushed 16 Aug 2026; docs updated July 2026
LicenceMIT SDK + proprietary hosted service

Domain fit

Tenki’s Firecracker-style microVM model supports memory-and-filesystem pause, snapshots and independent persistent volumes. Its published compute rates match Daytona/E2B’s unit rates, and it stops compute charging while idle.

Retention caveat

The CLI exposes --pause-retention, --sticky, --idle-timeout and --max-duration. Those are useful controls, but they also mean persistence depends on exactly how the community AgentBox provider creates sessions. The earlier research could not establish a sufficiently clear plugin default for unattended, arbitrary-length dormancy.

Use a persistent volume for durable workspace data and a snapshot for restoration; do not assume a paused session is permanent. Tenki’s terms also allow reclamation or deletion in capacity, non-payment and post-termination scenarios, reinforcing the need for off-provider copies.

Strengths and trade-offs

  • Strong full-state pause architecture and hardware-isolated VM boundary.
  • Independent volumes designed to outlive sessions.
  • Newer service and community integration mean less operational evidence.
  • Retention flags require an explicit tested policy, not hopeful defaults.

Fly Sprites

Verdict and best fit: Tier B Possibly the best filesystem-durability architecture here, but it does not promise indefinite process suspension and needs a custom AgentBox provider.

GitHub starsN/A
No canonical open-source service repository used for this comparison
MaintenanceActive managed service; documentation observed Aug 2026
LicenceProprietary hosted service

Domain fit

A Sprite writes to a normal ext4 filesystem on fast local storage while continuously syncing durable state to external object storage. The same paths return on every run and can remain dormant for months. This is unusually strong protection for dirty files.

Idle transition is two-stage. A warm Sprite preserves RAM and resumes processes in roughly 100–500 ms. Later, at a provider-controlled transition you cannot choose or observe, it goes cold, discards memory, and wakes with a fresh process start in roughly 1–2 seconds. Files survive both stages; the running agent survives only warm.

Integration

AgentBox does not ship a Sprites backend. Its provider SDK exposes a relatively small CloudBackend surface, so an integration is feasible, but the provider plugin would run as trusted host code and should be audited. Services can restart an agent on a cold boot; Tasks can keep active work running, but a forgotten keepalive can continue billing.

Strengths and trade-offs

  • Filesystem durability is continuous rather than dependent on a hibernation-time snapshot.
  • No compute billing while idle; storage is thin-provisioned and billed by use.
  • Exact process resume is temporary and not user-controlled over long dormancy.
  • Custom AgentBox engineering and maintenance are required.

Vercel Sandbox

Verdict and best fit: Tier C Good when the filesystem matters and restarting the agent is acceptable. Not a reliable fit for arbitrary long dormancy until snapshot expiration is explicitly configured and tested.

GitHub stars183 for vercel/sandbox
Observed 17 Aug 2026 UTC
MaintenanceActive; pushed 14 Aug 2026; latest release 7 Aug 2026
LicenceApache-2.0 SDK + hosted-service terms

Domain fit

A persistent Vercel sandbox snapshots its filesystem when the session stops and restores that filesystem into a new session. AgentBox therefore maps pause to stop and resume to start. Your workspace, packages and caches return; the previous Claude/Codex process does not.

Retention and runtime

Vercel snapshots expire 30 days after last use by default. Vercel’s own SDK and CLI can set a custom expiry or no expiry, but the original research did not find an equivalent AgentBox configuration key. Treat a forgotten AgentBox/Vercel box as at risk after a month unless the effective policy is verified in the provider account.

Vercel currently documents up to 24 hours per session on Pro/Enterprise and 45 minutes on Hobby. This improved in June 2026; AgentBox documentation may lag some provider limits, so test the exact integration.

Strengths and trade-offs

  • Simple built-in AgentBox experience and stable filesystem resume.
  • No paused compute cost.
  • No exact process continuation.
  • Default 30-day snapshot expiry conflicts directly with “forget it indefinitely.”

Hetzner Cloud VPS

Verdict and best fit: Tier C A credible, inexpensive pet-box choice for a small number of long-lived agents. It offers dependable disk semantics, not memory suspension.

GitHub starsN/A
Managed infrastructure product
MaintenanceActive service and built-in AgentBox provider
LicenceProprietary service

Domain fit

AgentBox provisions one complete VPS per box. Its pause is a power-off/power-on cycle: the disk remains, while RAM, tmux and the live agent process do not. Full-disk snapshots provide a reconstruction point. The documented AgentBox default is a 2-vCPU / 4-GB / 40-GB cx23 at roughly €4/month.

Economics and lifecycle

Hetzner bills the server while it exists, regardless of power state. For long idle periods you can snapshot and delete it, then recreate later, but that is a disk restore rather than exact process resume. At roughly €4 per box, simply leaving a handful running can still be perfectly rational.

Remote Docker is normally better when you want many boxes: one larger VPS can host several containers, whereas the built-in Hetzner provider allocates a separate VM and bill to each box.

DigitalOcean Droplet

Verdict and best fit: Tier C Operationally straightforward and region-flexible, including London, but comparatively expensive per permanent AgentBox box and unable to resume a suspended process.

GitHub starsN/A
Managed infrastructure product
MaintenanceActive service and built-in AgentBox provider
LicenceProprietary service

Domain fit

Like Hetzner, AgentBox creates one VM per box. Pause means power-off, which preserves disk but not RAM or running processes. AgentBox maps checkpoints to Droplet snapshots. DigitalOcean’s documented default in AgentBox is 2 vCPU / 4 GB / 80 GB at about $24/month, with lon1 available for UK latency.

Economics and lifecycle

DigitalOcean explicitly says powered-off Droplets remain billable; destroying is required to stop compute charges. Snapshots are on-demand disk images and may be taken live, though DigitalOcean recommends power-off for applications that need a consistent disk state.

Choose this over Hetzner mainly for region, account familiarity or surrounding DigitalOcean services—not for persistence semantics. Choose Remote Docker over either pet-VM provider when you want to amortise one server across many boxes.

Implementation recommendation

A no-loss operating model that works with any provider

1Choose the resume layerRemote Docker pause for fixed-cost control, or Daytona/E2B for managed full-state suspend.
2Checkpoint intentionallyCreate a disk/full-state checkpoint after setup and before risky work. Do not assume an idle timeout creates one.
3Export work automaticallyAt a short interval, commit to an agent branch or create a Git bundle and copy it off the sandbox host.
4Back up outside the failure domainUse another provider/account or storage target with versioning and retention. A snapshot in the same account is helpful, not independent.
5Test destructive casesProve resume after idle, host reboot, provider timeout, sandbox deletion and restore. Check both dirty files and the running-process marker.
6Monitor the contractAlert on unpushed branches, stale backups, near runtime caps, snapshot expiry and boxes that failed to auto-pause.
Recommended pilot: one Remote Docker VPS, one Daytona Linux VM and one E2B sandbox. Run the same 48-hour test fixture in each, including a 24-hour idle period, a deliberate host/provider interruption and a restore after deleting the live sandbox. The cheapest provider that passes your recovery test—not the prettiest pause demo—wins.

Minimum acceptance checklist

  • Dirty tracked and untracked files survive an ordinary idle cycle.
  • A running marker process resumes where expected on providers claiming memory suspend.
  • A checkpoint restores after the original box is deleted.
  • An off-provider copy restores after the provider account or VPS is unavailable.
  • Idle and active billing match the expected lifecycle state.
  • The exact AgentBox release, plan and retention settings are recorded.

Methodology, scope and evidence limits

This report converts and refreshes the research from the referenced “Agent Persistence Comparison” conversation. The comparison set preserves its providers: Remote Docker, Daytona, E2B, Tenki, Fly Sprites, Vercel, Hetzner and DigitalOcean. AgentBox’s seven built-in backends include local Docker, Remote Docker, Hetzner, DigitalOcean, Daytona, Vercel and E2B; Tenki is a community integration and Sprites requires a custom provider. Local Docker is omitted because the user’s decision is specifically remote execution.

The ranking weights: exact resume after idle; dirty-file survival; retention without hidden deletion TTL; recovery after sandbox deletion; independence from one host/account; continuous active-run limits; idle economics; AgentBox integration maturity; and UK latency. Provider and AgentBox documentation were checked on 17 August 2026 UTC. Repository star counts and push/release metadata were observed on the same date. Stars measure attention, not quality, and are N/A where a service has no canonical repository relevant to its persistence contract.

Licences describe public SDKs/cores, not the hosted service contract. Daytona’s former core repository is retained for historical popularity context, but the hosted product should not be described as open source after its 2026 closure announcement. This report is operational analysis, not legal advice or a service-level guarantee.

Material limits remain: AgentBox and sandbox providers were evolving quickly in mid-2026; provider docs and AgentBox mappings sometimes lag one another; account tier, region and integration version can change lifecycle behaviour. The definitive validation is an end-to-end persistence test under your exact plan and AgentBox release.

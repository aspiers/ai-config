Evidence-led FOSS comparison

Branches, worktrees, and integration mixes for an AI development cockpit

A detailed comparison of Git-native and next-generation FOSS tools for tracking many branches against upstream, making each branch easy to develop and test, and composing active work into one runnable integration target. It refreshes earlier research recovered through the local AgentsView history and evaluates the tools against a Herdr + AgentBox cockpit architecture.

Evidence observed 25 August 2026 UTC · 12 detailed candidates · GitHub activity window 25 August 2025–25 August 2026

⚠️ Author-specific architecture. The recommendations below are evaluated against Adam Spiers’ planned Herdr + Collie + AgentBox cockpit and its existing Worktrunk and branch-mixer integrations. Other readers should reuse the capability evidence and ownership model, but substitute their own control plane, sandbox, workspace and publication constraints before adopting the recommended stack.

Bottom line

Keep the solution layered; use one authority per concern

Recommended remote-cockpit stack: Worktrunk for host/control-plane worktree lifecycle, Git Machete for explicit branch dependency topology and upstream synchronization, AgentBox for remote box and agent lifecycle, Herdr for interactive presentation, and ggmx/ggmxd for the disposable, unpublished fan-in branch. Git Machete and worktrunk-sync should not both write topology for the same repository. T3 Code merits a separate control-surface pilot: it can replace much of the Herdr/Collie experience for supported agents, but its native worktree and session ownership should not be layered casually on top of Worktrunk. git-stint is a second local lifecycle lane, not another layer: trial it instead of Worktrunk for Claude Code sessions, while retaining ggmxd for a durable, continuously refreshed mix.

Local, all-worktree repos

Worktrunk + worktrunk-sync is the smallest natural pilot when every active branch has a Worktrunk worktree. Start with dry runs and no push/prune.

Remote AgentBox cockpit

Worktrunk + Git Machete is the better default because cloud boxes are independent clones and scratch branches, not host Worktrunk worktrees.

Holistic challenger

Stax is the most cockpit-like all-in-one pilot; Stackit is the runner-up. Both are only about eight months old and overlap existing layers.

Agent-native control surface

T3 Code is the strongest web/desktop/mobile agent-harness candidate. Pilot it as an alternative execution lane, not as branch topology or a second worktree authority.

Claude-local alternative

git-stint tightly couples one agent session to one branch and worktree, with checkpoints and temporary combined tests. Pilot it instead of Worktrunk, not beside it.

Strategic alternative

Jujutsu has the most coherent native primitives, including multi-parent merge changes, but adopting it changes the VCS model rather than adding a Git helper.

The category distinction that prevents a bad tool choice

A stack records dependency: child B contains or depends on parent A, so restacking B on a rewritten A is meaningful. A mix is a temporary fan-in of unrelated peers A, B, and C solely so the combined result can run. Most stack tools can make the tip of one linear stack contain its ancestors; that is not an arbitrary, refreshable integration mix.

Recommended cockpit ownership model

The design works when each state machine has a narrow boundary. Herdr displays and controls sessions; it should not independently create Git worktrees. AgentBox owns remote execution state; its status can be projected into Herdr, but duplicated markers are caches.

Concrete seams already present

  • The installed Herdr–Worktrunk integration follows the right ownership pattern: it calls wt switch --no-cd --format=json, resolves the path, then registers it with herdr worktree open. Removal is delegated to guarded wt remove before Herdr closes the view.
  • Worktrunk hooks and agentbox.yaml can both install dependencies and start services. Use Worktrunk configuration only for host worktrees, AgentBox configuration inside boxes, and have both call shared repository task-runner targets.
  • For stacked chains, the topology tool restacks/reparents first; Worktrunk only performs lifecycle cleanup afterward. Otherwise wt merge can rebase/remove a parent while children still refer to it.
  • Serialize restacks, scratch-branch landing, worktree removal and mixdown behind a repository-level orchestration lock. An agent working on a branch that is force-rewritten elsewhere becomes stale even when each individual tool behaves correctly.
  • T3 Code can list and reuse worktrees found through Git, but its native workflow also creates/removes worktrees and pins running threads to them. There is no documented lifecycle-delegation plug-in equivalent to the Herdr–Worktrunk seam.
  • git-stint is another lifecycle-owning alternative. If trialled, let it own the repository’s local session worktrees and Claude hooks instead of Worktrunk; do not treat its temporary combined-test worktree as the persistent mixer target.
Remote versus local matters. Local Docker AgentBox can create a linked Git worktree whose working directory exists only inside the container; host tools can see a stale-looking worktree record and must not clean it. The planned remote-only cockpit avoids that collision because cloud boxes use independent clones and scratch refs. AgentBox remains their sole lifecycle owner.
T3 Code changes the execution boundary. Its server owns provider processes, terminals, Git and filesystem access on the machine where the server runs. Putting that server on the trusted orchestrator would run agents there, contrary to the remote-box isolation plan. A T3-native experiment should instead place a T3 server inside or alongside a disposable remote development environment and treat its state and lifecycle as part of that environment. This is an architectural experiment, not a documented AgentBox integration.

Reference remote workflow

1 · Canonical branchRegister one source branch in the chosen topology and, if needed, a host Worktrunk checkout.
2 · Remote boxStart AgentBox from that ref and work on an isolated agentbox/<box> scratch branch.
3 · ObserveHerdr attaches and presents the AgentBox-owned agent state without becoming a second authority.
4 · PromoteLand scratch work host-only, review it, then integrate into the canonical branch and restack descendants.
5 · Mix and testRebuild the unpublished mix after restacking; seed a disposable box from its tip for combined testing.
Exclude ephemeral refs from topology. Omit the mix target and agentbox/* branches from Machete and worktrunk-sync until explicitly promoted. If a legacy mix target must remain visible in Machete, protect it with push=no rebase=no slide-out=no.

Alternative T3-native lane

For a representative disposable repository, let T3 Code—not Worktrunk—create the thread worktrees, start the supported agent CLI, run checked-in setup/project scripts, show diffs and PRs, and provide web/mobile control. Keep Git Machete or git-spice outside the live editing loop as the single dependency-topology authority, operating only after T3 threads are quiescent and under the same repository lock. A dedicated T3 worktree can host the unpublished ggmxd target. This lane tests whether T3 Code can replace the Herdr/Collie plus Worktrunk interaction layer; it should not be blended with that layer until external-worktree bugs and ownership APIs are resolved.

Worktrunk

Verdict: Best worktree and branch-development chassis. It solves the second requirement exceptionally well and provides the composable hooks/JSON needed by the cockpit, but it is deliberately not a full dependency-topology or arbitrary-mix engine.

GitHub stars6,606 as of 25 August 2026
Maintenance4,919 default-branch commits in the one-year window; latest 25 August 2026; v0.74.0 on 14 August
LicenceMIT OR Apache-2.0

Domain fit

Worktrunk maps branches to predictable worktree paths and makes creation, switching, setup and agent launch a single action. wt list combines dirty status, default-branch difference, upstream ahead/behind, optional PR/CI state, development URL and agent markers; JSON output makes it a strong data source for a cockpit dashboard.

Development experience

wt switch --create branch -x agent can create a branch/worktree, run approved setup hooks and start a tool with full terminal control. Ten lifecycle hook points cover create, switch, start, commit, merge and remove. Recipes cover copied ignored caches, deterministic ports, per-worktree databases and pre-merge validation.

Upstream and combining

It displays tracking divergence and can create a local branch from a remote-only branch, but merge operations are intentionally local and do not fetch or publish. wt merge can integrate one branch into a target, usually with rebase/squash and cleanup, but this is an imperative landing pipeline—not a persistent dependency tree or declarative multi-peer mix.

Strengths and trade-offs

  • Strength: hooks, aliases, arbitrary wt-<name> extensions, JSON and generic --execute make it the most composable local layer.
  • Strength: agent integrations and per-worktree environment conventions directly support parallel AI development.
  • Trade-off: simple --base branching does not maintain a stack forest or restack descendants.
  • Operational rule: let the topology manager reconcile children before Worktrunk merges/removes a stacked parent.

T3 Code

Verdict: Highly relevant as an agent-native cockpit and the strongest reviewed web/desktop/mobile control-surface candidate. It makes branch/worktree development unusually accessible, but it does not model dependency topology or mix branches, and its native ownership overlaps Worktrunk, Herdr and parts of AgentBox.

GitHub stars20,416 as of 25 August 2026
Maintenance2,810 default-branch commits since creation on 8 February 2026; latest 25 August; v0.0.33 on 10 August
LicenceMIT for the repository; agent providers remain separate dependencies

Domain fit

T3 Code describes itself as an “agent harness control surface”. Its server owns agent sessions, workspaces, version control, terminals and filesystem operations; web, Electron desktop and mobile clients connect over authenticated RPC. Built-in drivers support Codex, Claude Code, Cursor, Grok Build and OpenCode. Threads carry project, branch and worktree context, and per-turn checkpoints are stored as hidden Git refs so diffs and reverts can be associated with agent turns.

Branches, worktrees and upstream

The branch picker lists local, remote, default, current and already-worktreed refs; it can create/switch refs, reuse a detected worktree, or create a fresh branch/worktree from an explicitly selected base. Worktree-mode bootstrap can resolve the latest fetched remote commit, and checked-in t3.json scripts can run automatically after creation. T3 Code also clones and publishes repositories, shows ahead/behind and PR status, and supports PR/MR creation and review for GitHub, GitLab, Bitbucket and Azure DevOps.

This is strong per-branch development and forge integration, but only partial multi-branch management: there is no dependency forest, parent-first restack, or bulk synchronization of an active branch set. The internal operation named runStackedAction is a sequential branch/commit/push/PR transaction, not stacked-branch support.

Combining branches

There is no first-class arbitrary fan-in mix. A checked-in project script could invoke ggmxd and open a preview in a dedicated integration worktree, which makes T3 Code a good consumer of the mix, but the mix registry, safety checks and unpublished target remain external responsibilities.

Cockpit composition

  • Potential replacement lane: T3 Code could replace much of Herdr + Collie for supported agents by adding a structured conversation UI, approvals, diffs, PR review, terminals, web access and native mobile clients.
  • Worktrunk overlap: both want to create, initialize, locate and remove worktrees. T3 can reuse existing worktrees discovered through Git, but it has no documented Worktrunk delegation plug-in or lifecycle API.
  • AgentBox boundary: T3’s server executes the agent CLI where it runs; it does not natively provision AgentBox boxes, operate the AgentBox queue or use its host relay. Running a T3 server inside a disposable box is plausible but not a documented integration.
  • Topology: Git Machete or git-spice can remain the sole dependency authority, but must not rewrite branches checked out by live T3 threads. Quiesce threads and take the repository lock first.

Maturity and current worktree risks

The repository is not archived and its activity is exceptionally high, but it is only six months old; the README explicitly says the project is “very very early” and to expect bugs. Open user reports directly relevant to composition include external worktrees being shown as Local, an external-worktree path leading commit/push/PR actions toward the main checkout, two threads sharing one worktree while displaying conflicting branches, and a running thread becoming wedged when another tool removes its worktree. These reports are not independent reproductions, but they make dual lifecycle ownership inappropriate today.

Licence and dependency boundary

The monorepo carries a conventional MIT licence, including server and client source. The complete experience still depends on separately installed agent CLIs and their authentication/subscriptions; T3 Code being FOSS does not make every provider FOSS. An OpenCode-only deployment can keep more of the agent path open, while Codex, Claude, Cursor and Grok retain their own service and licence boundaries.

Recommendation

Give T3 Code a first-class disposable-environment pilot, not just a mention. Compare a T3-native lane against the existing Herdr/Worktrunk lane on mobile control, agent resume, multiple concurrent worktrees, setup scripts, PR review and crash recovery. In that pilot, let T3 own its worktrees; do not use T3’s commit/push controls on Worktrunk-created worktrees until the external-worktree issues are fixed and verified.

worktrunk-sync

Verdict: The smallest, most natural topology companion for a purely local Worktrunk workflow in which every active branch has a worktree. Its youth, inferred topology and incomplete licence hygiene make it a controlled pilot, not the global cockpit authority.

GitHub stars16 as of 25 August 2026
Maintenance41 total commits; last default-branch activity and v0.1.2 on 29 April 2026
LicenceMIT declared; no full root licence text observed

Domain fit

It discovers parent/child relationships from merge bases among branches that have worktrees, stores a Machete-compatible tree in .git/wt/stack, and records fork points so rewritten parents can be handled with git rebase --onto without duplicating commits. Parent-first topological execution supports one stack or all stacks.

Development and upstream workflow

It is deliberately a narrow wt-sync/wt sync companion. Flags can fetch, rebase, force-push-with-lease and prune integrated worktrees; dry-run, verbose planning and resumable conflicts are available. It does not create environments, launch agents, display CI or create PRs.

Combining branches

It updates dependency stacks. Sibling branches remain siblings; it has no aggregate test branch and does not replace ggmxd.

Strengths and trade-offs

  • Strength: almost zero ceremony for a branch-per-worktree local repo.
  • Trade-off: remote AgentBox branches that lack host worktrees are invisible to its participation model.
  • Trade-off: format compatibility is not shared state—.git/wt/stack and .git/machete are separate files and can drift.
  • Licence caution: Cargo and README declare MIT, but the repository lacks the governing full licence text normally expected for confident redistribution.

Git Machete

Verdict: Strongest mature branch-relationship and upstream engine for the remote cockpit. Its explicit forest remains meaningful even when active work happens in independent AgentBox clones rather than host worktrees.

GitHub stars1,135 as of 25 August 2026
Maintenance284 default-branch commits in the window; latest 23 August 2026; v3.44.1 on 7 July
LicenceMIT

Domain fit

An editable .git/machete forest declares branch dependencies. discover proposes a layout, status marks edges as in-sync, out-of-sync or merged, and traverse can synchronize parents and remote tracking branches, resume after conflicts, and create or retarget GitHub PRs and GitLab MRs.

Worktrees and development

The top-level layout is shared across worktrees. Traversal changes into a branch’s owning worktree when present; for an unmaterialized branch it can use a temporary worktree. This is genuine worktree awareness, but permanent path provisioning, setup hooks, dev servers and agent launch remain Worktrunk’s job.

Combining branches

The tip of a linear stack naturally includes ancestor work, and advance can fast-forward a parent to one child. There is no arbitrary sibling-to-aggregate command; forcing unrelated peers into a stack changes dependency semantics and is not a substitute for a disposable mix.

Cockpit configuration

  • Use one explicit allowlisted topology and keep agentbox/* and mix refs outside it until promotion.
  • Set machete.traverse.push=false so traversal does not publish by default.
  • Set machete.traverse.whenBranchNotCheckedOutInAnyWorktree=cd-into-temporary-worktree for central orchestration.
  • Do not run worktrunk-sync as a second mutating topology authority.

ggmx + ggmxd

Verdict: Retain. It is the only reviewed Git-native tool whose primary abstraction is exactly the requested arbitrary, ordered set of active peer branches merged into a disposable local target.

GitHub stars105 for the containing git-config repository as of 25 August 2026
Maintenance28 default-branch commits in the one-year window; latest 25 August 2026; no tagged release
LicenceGPL-3.0-or-later in source headers

Domain fit

git mix records an ordered branch set in Git configuration. git mixdown rebuilds the target from its base with git checkout -B, then merges the remaining branches—octopus by default—and optionally stays on the target. The target is a throw-away integration branch, never a publication branch.

Development and upstream workflow

It does not manage upstreams, dependency topology, worktrees or environments. That narrowness is an architectural advantage when paired with Worktrunk and Machete: the mixer never pretends peer branches depend on one another. A dedicated integration worktree or disposable test box provides the development environment around it.

Safety and observability gaps

  • The target is forcibly recreated; add clean-tree and “checked out in another worktree” preflight checks.
  • Add a dry-run and structured JSON plan/result so the cockpit can show inputs, base, merge order, conflicts and resulting tip.
  • Use a dedicated target/ref namespace plus a repository orchestration lock.
  • Surface conflict state explicitly; octopus merges abort when conflicts require human resolution.
  • Exclude mix targets from topology tools and all push/PR automation.

git-spice

Verdict: Best cleanly composable alternative to Machete when offline-first stack operations and broad forge support are the priority. It fits above Worktrunk without trying to replace Herdr, AgentBox or the mixer.

GitHub stars750 as of 25 August 2026
Maintenance461 default-branch commits in the window; latest 24 August 2026; v0.31.2 on 21 July
LicenceGPL-3.0

Domain fit

git-spice tracks branch stacks in local metadata, creates/navigates branches, restacks a branch, stack or repository, synchronizes trunk and submits/lands stacks. It works locally and offline, then integrates with GitHub, GitLab, Bitbucket, Gitea, Forgejo and Codeberg-style workflows.

Worktrees and development

Worktrees are compatible but not a first-class owned lifecycle. The official recipes demonstrate a custom branch-picker alias around git worktree add. In this cockpit, Worktrunk should remain responsible for paths, hooks and agent launch while git-spice owns lineage and forge actions.

Combining branches

Bottom-up stack landing can consolidate dependent work, but there is no persistent arbitrary peer mixer. Keep ggmxd.

Strengths and trade-offs

  • Strength: broad forge coverage and local/offline metadata reduce service coupling.
  • Strength: narrow responsibility composes cleanly with Worktrunk, Herdr and AgentBox.
  • Trade-off: less mature and less explicitly worktree-aware than Git Machete; permanent worktrees need another layer.

Stax

Verdict: Strongest holistic FOSS cockpit pilot. It combines stacks, real worktrees, parallel agent lanes, TUI/GUI, tmux, status and arbitrary launch commands—but overlaps three existing layers and is only about eight months old.

GitHub stars123 as of 25 August 2026
Maintenance1,111 default-branch commits in the window; latest 24 August 2026; v0.105.1 on 23 August; repository created December 2025
LicenceMIT

Domain fit

Stax manages branch stacks and synchronization while “lanes” give parallel agents real branches and worktrees. It includes TUI and GUI views, CI/review status, undo/redo, warm worktree slots, tmux reattachment, and launchers or skills for Codex, Claude, Gemini, OpenCode and Pi. Parallel commands can run in temporary worktrees.

Cockpit composition

The opinionated lane shortcut prefers tmux and a fixed agent list, so Herdr composition would likely use general worktree commands or a no-tmux mode. Its UI and lane state overlap Herdr, Worktrunk and AgentBox and must not become competing authorities.

Combining branches

Merge/cascade operations act on a dependency stack. They do not maintain a named, arbitrary set of independent peers as a continuously rebuilt test target. Stax therefore challenges the lifecycle/topology stack, not ggmx.

Strengths and trade-offs

  • Strength: closest single-project match to the cockpit’s agent/worktree/operator experience.
  • Strength: machine-readable commands and arbitrary launch hooks preserve some composability.
  • Trade-off: intense activity is not a substitute for operational maturity; pilot in disposable repositories.
  • Security rule: its “yolo” lane option forwards agent sandbox/approval bypasses; worktree isolation is not security isolation, so keep AgentBox for containment.

Stackit

Verdict: Second holistic pilot. It has an unusually complete stack/worktree/agent/dashboard feature set, but its age, rapid churn and destructive cleanup boundary demand explicit safety trials before adoption.

GitHub stars32 as of 25 August 2026
Maintenance2,620 default-branch commits in the window; latest 25 August 2026; v0.26.1 on 17 August; repository created December 2025

Domain fit

Stackit tracks tree-shaped stacks, automatically restacks, submits/merges GitHub PRs and has repository-level undo. Its managed worktrees include hooks, hidden anchors, ownership and worktree run; JSON state, parallel foreach, generated agent skills and an experimental local web dashboard are unusually cockpit-friendly.

  • Only a few dozen stars and a very young repository make its high commit volume evidence of velocity, not durability.

Jujutsu

Verdict: Best strategic alternative and closest principled replacement for mixer semantics. It can unify workspaces, DAG rewriting, undo, parallel execution and synthetic merge changes—but only by adopting a different VCS mental model and compatibility envelope.

GitHub stars31,185 as of 25 August 2026
Maintenance1,928 default-branch commits in the window; latest 25 August 2026; v0.44.0 on 6 August
LicenceApache-2.0

Domain fit

Jujutsu is a VCS rather than a Git workflow wrapper. Native workspaces provide multiple working copies backed by one repository; bookmarks map to Git branches and can track remotes; rewritten descendants automatically rebase; conflicts are first-class objects; repository operations are undoable. jj run can execute revisions in isolated working copies and in parallel.

Combining branches

jj new A B C creates a multi-parent merge working-copy change, giving the strongest reviewed foundation for a live combined-test change. It is not identical to a declarative mix registry/daemon: when a bookmark advances by adding a child rather than rewriting its current head, the merge change may need explicit update.

Adoption boundary

Colocated Git repositories preserve substantial interoperability, but Jujutsu workspaces replace Git worktrees rather than compose with Worktrunk. Current compatibility documentation calls out missing Git hooks, .gitattributes, submodules, partial clones, Git LFS and git worktree support. GitHub flow also uses explicit fetch/rebase/bookmark operations rather than a direct pull analogue.

Recommendation

Run a separate representative-repository experiment. Do not insert Jujutsu halfway into the production cockpit and expect Git Machete/Worktrunk semantics to remain authoritative.

git-stint

Verdict: A promising local, Claude-Code-centric alternative to Worktrunk rather than a companion to it. It couples each agent session to a real branch and worktree, adds automatic WIP checkpoints and cleanup, and can test a disposable combination of selected session branches. GitHub stars35 as of 25 August 2026
Maintenance79 default-branch commits since creation on 27 February 2026; latest main commit 20 June was dependency automation; npm v0.6.1 on 28 March; no GitHub release
LicenceMIT

Domain fit

git stint start NAME creates a stint/NAME branch, a .stint/NAME worktree and a session manifest under .git/sessions/. Commands cover status, diff, checkpoints, commits, squashing, merging, GitHub pull requests, resume, cleanup, undo and stale-session pruning. Claude Code hooks redirect write tools into the stint worktree and create a WIP checkpoint when the agent stops. The branches remain ordinary Git branches, but the native autonomous adapter is Claude-specific; Codex, OpenCode and Pi would use the CLI manually unless adapters are added.

Combining branches

git stint test --combine A B creates a temporary detached worktree and branch from the default branch, merges the selected stint branches, runs the configured test command, then removes both temporary objects. This is the closest direct partial match to the mixer requirement among the Git worktree managers: it is useful for one-shot combined validation, but there is no named membership registry, daemon, reusable tip or continuously refreshed branch to seed another environment.

Composition, ownership and trust boundary

  • Worktree authority: git-stint and Worktrunk both create, configure, list and remove worktrees. Choose one for a repository; dual ownership would make cleanup and session state ambiguous.
  • Topology: stint sessions are peers. There is no parent/child dependency forest or descendant restacking, so Git Machete or git-spice remains a separate quiescent-phase authority if stacks are needed.
  • Cockpit: manifests plus list --json, status and checkpoints provide useful local observability, but not Herdr/T3-style presentation, mobile control, remote execution or a broad structured control API.
  • Isolation: configured shared files and directories are symlinked back to the main checkout. That is convenient for caches, but it deliberately shares mutable state and can expose credentials such as .env files across sessions. post_create also executes configured shell code. Treat both as trusted repository configuration, not sandboxing.
  • Conflict signal: conflicts reports overlapping changed paths across sessions. It is an early coordination warning, not proof of a textual or semantic merge conflict.
  • Maturity: the code is small and has no runtime dependencies, but the project is less than six months old. Three open pull requests were Dependabot updates; the latest main activity was also dependency automation, so present maintenance is uncertain despite the initial burst.

Recommendation

Pilot v0.6.1 in a disposable Claude Code repository as an alternative local lane. Compare its automatic redirection, stop checkpoints, crash recovery and cleanup with Worktrunk’s broader hooks and agent integration. Keep secrets out of shared links, inspect post_create, and verify that test --combine removes its temporary worktree after success, failure and interruption. Retain ggmxd for any durable mix consumed by other agents or boxes.

Methodology, scope and exclusions

Research began by confirming the local AgentsView MCP was callable and searching prior task/session content for worktrunk-sync, Git Machete, branch mixing, T3 Code and the cockpit plan. FOSS boundary

  • GitButler was excluded from the FOSS shortlist because its FSL-1.1-MIT “Fair Source” licence has a non-compete period and is not OSI-compatible today, even though it later converts to MIT. Project announcement.
  • Graphite was excluded because the defining current CLI/service workflow is not available as a clean self-contained FOSS solution and PR operations require a Graphite account/token. Installation/account boundary.
  • GitHub stacked PRs / gh-stack are useful adjuncts, but the defining remote service is proprietary GitHub, so they are not an end-to-end FOSS solution. GitHub stacked PR documentation.
  • StGit remains a good GPL-2.0 patch-series specialist, and Sapling a credible GPLv2 VCS/stack replacement; neither is as strong a fit as the detailed shortlist for shared multi-workspace control plus arbitrary fan-in.
  • worktrunk-sync remains in the table because its source and package metadata clearly declare MIT intent, but the missing full licence file is stated as a material hygiene defect rather than silently treating it as cleanly licensed.
  • T3 Code itself is MIT-licensed FOSS, but most supported agent providers and their hosted model services retain separate licences, accounts and subscription boundaries. The report rates the T3 Code control surface, not those providers as a combined FOSS stack.

Interpretive limits

Documented features were distinguished from inferences and workarounds. Issue reports are evidence of current risk, not independent reproduction of every defect. The cockpit recommendation is architecture-specific: a local all-worktree setup and a remote independent-clone AgentBox setup lead to different topology choices.

Needs-based recommendation and pilot plan

  1. Production architecture: keep Worktrunk as the host worktree/development layer, Git Machete as the remote-cockpit topology authority, AgentBox as the remote execution authority, Herdr as the UI/control surface, and ggmx/ggmxd as the isolated fan-in layer.
  2. Local pilot: trial worktrunk-sync in a disposable clone where every branch has a Worktrunk worktree. Begin with --dry-run; do not enable push or prune until topology inference and conflict recovery are trusted. Ask upstream to add a complete licence file.
  3. Modular alternative pilot: trial git-spice above Worktrunk if multi-forge submission and offline stack operations matter more than Machete’s explicit worktree-aware traversal.
  4. Agent-native cockpit pilot: run T3 Code in a disposable remote environment as an alternative to the Herdr/Collie + Worktrunk interaction layer. Let T3 own that environment’s threads and worktrees; measure mobile control, recovery and PR flow, and do not use its publication controls on externally managed worktrees while the current reports remain open.
  5. Local Claude-session alternative: trial git-stint in a disposable repository instead of Worktrunk. Assess automatic edit redirection, checkpoints, crash recovery, cleanup, shared-state boundaries and test --combine; keep ggmxd for durable mixes.
  6. Holistic challenger: evaluate Stax first and Stackit second in disposable repositories. Measure whether their combined UI/agent/worktree state can replace—not duplicate—Worktrunk and Herdr. For Stackit, disable automatic cleanup and verify ignored-file recovery.
  7. Strategic track: evaluate Jujutsu separately on a representative repo containing hooks, LFS/submodules if relevant, multiple workspaces, remote collaboration and a multi-parent combined-test change.
  8. Mixer hardening: add dry-run, JSON, worktree/cleanliness preflight, explicit conflict output, a dedicated ref namespace and repository lock to ggmxd. Keep mix targets unpushable and outside all stack topology.

Acceptance tests for the cockpit pilot

  • Create three independent branches, materialize any local worktrees, and start local and remote agents without path, port or branch collisions.
  • Rewrite a parent branch and prove only the chosen topology authority restacks descendants; active boxes must be detected, paused or explicitly resynchronized.
  • Rebuild one combined-test target from two unrelated siblings and one stacked tip, run tests in a disposable box, then prove no publication command can push that target.
  • Crash during a conflict and demonstrate inspectable, resumable state without deleting dirty or ignored files.
  • In the T3-native lane, create and resume three agent threads across separate worktrees from desktop and mobile, then remove one worktree while idle and prove the thread remains recoverable. Separately verify that an externally created worktree is either recognized correctly or blocked from T3 commit/push controls.
  • In the git-stint lane, crash one of two Claude sessions, recover its last checkpoint, run test --combine, and prove its temporary branch and worktree are removed after both a passing and failing test. Confirm that no shared secret or mutable file crosses session boundaries unexpectedly.
  • Render a unified read-only cockpit view by joining Worktrunk JSON, topology status, AgentBox lifecycle and Herdr presentation through explicit branch/worktree/box identifiers.

Enhancing git-machete to replace ggrbm

Proposal dated 7 September 2026

⚠️ AUTHOR-SPECIFIC SCOPE: This report analyzes the maintainer’s deployed ~/bin/ggrbm and current local checkout inventory. The design is reusable, but the paths and inventory observations are specific to this setup.

Decision

Enhance git-machete upstream, then retire ggrbm. Do not build a second full orchestration engine locally.

Git-machete already owns the hard domain logic: branch graphs, fork-point inference, parent-before-child traversal, update semantics, hooks, and linked-worktree handling. A substantial standalone rewrite of ggrbm would duplicate that logic behind a weaker public interface and would drift as git-machete evolves.

The missing upstream capability is a narrow, deterministic rebase mode with a machine-readable plan. It should select only rebases, never implicitly pull, reset, push, slide out branches, rewrite the layout, or perform code-hosting operations. The plan should freeze refs and fork points, support explicit approval, create recovery refs, and stop with structured resume state on a conflict.

The preferred lifecycle is therefore:

  1. Propose the deterministic planning contract upstream.
  2. Implement it inside git-machete, reusing its internal graph, update, hook, and worktree machinery.
  3. Keep ggrbm temporarily as a thin policy shim for local whitespace checks and compatibility while the upstream feature lands.
  4. Retire the shim once callers can invoke the upstream command directly.

“Deterministic” here means deterministic inputs, ordering, decisions, side effects, and recovery. A rebase cannot promise identical commit hashes across runs because commit timestamps, hooks, Git versions, and conflict resolutions can change them.

Why the current script should be replaced

The current ggrbm has served since 2009, but its control model assumes a person is sitting at a terminal.

Current behavior Consequence for an agent
Reads ordered git rebase argument lists from .git/topic-branches Duplicates the branch graph now owned by .git/machete, with no graph validation
Launches bash after a failed command or conflicted rebase Hides state inside a nested interactive shell and gives the caller no structured resume point
Prompts after whitespace findings and after recovered failures Requires a TTY and makes policy decisions during mutation
Accepts arbitrary !git ... commands in the same file Makes a rebase plan capable of unrelated ref, checkout, merge, and remote changes
Mutates one branch at a time with no up-front snapshot A late invalid branch or dirty worktree is discovered only after earlier refs moved

There are also concrete failure cases:

  • A failed git rebase that leaves neither rebase-apply nor rebase-merge can be reported as done and processing continues.
  • The initial in-progress check only examines $root/.git/rebase-apply, which is incomplete for merge-backend rebases and linked worktrees.
  • The custom config is trusted for ordering. It cannot reject a child-before-parent sequence, duplicate branch, cycle, stale ref, or repeated rebase.
  • Whitespace checking uses the configured upstream-to-branch range rather than the exact fork-point-to-branch range that will be replayed.
  • Recovery depends on reflogs and the operator remembering where execution stopped. The script creates no named backup refs or machine-readable journal.

The useful behaviors are worth preserving: process a set in dependency order, check commits before replay, restore the original checkout when safe, and pause rather than guessing through conflicts.

Why plain traverse -y is the wrong default

git machete traverse already walks layout order, understands worktrees, rebases branches, and can run without prompts. The tempting replacement is: 

git machete traverse --yes --no-push --return-to=here

That command is broader than ggrbm should be. According to the git-machete traverse reference, traversal can also:

  • pull a branch that is behind its remote counterpart;
  • reset a diverged branch to a newer remote counterpart;
  • slide a merged branch out of .git/machete;
  • rewrite .git/machete as part of slide-out;
  • push unless --no-push is supplied explicitly.

--no-push disables pushes, not remote pulls, remote resets, or slide-out. --yes removes prompts by accepting git-machete’s proposed actions. That is automation, but it is not a narrow or inspectable rebase plan.

Keep traverse -y --no-push available as an explicitly selected convenience for repositories whose policy accepts all of those behaviors. The gap is best closed inside git-machete with an operation allowlist and a plan/apply contract, rather than by reproducing traversal in ggrbm.

Upstream status

The canonical tracker already contains adjacent work. Open issue #1210 requests machine-readable JSON status. A maintainer explicitly invited a pull request and acknowledged that downstream integrations need stable plumbing rather than access to git-machete’s private Python objects.

Closed issue #293 introduced branch qualifiers such as rebase=no and push=no. Closed issue #1619 and merged PR #1626 show continuing upstream interest in safer traversal behavior.

No existing issue or open pull request was found for the complete deterministic rebase-only plan/apply mode. That search is evidence, not proof of absence; a focused upstream proposal should reference #1210 rather than duplicate it.

Proposed upstream architecture

1. One source of branch structure

Retire .git/topic-branches. The upstream implementation should consume git-machete’s internal branch-layout model directly, preserving layout order as the deterministic tie-breaker between independent siblings. It should not shell out to its own CLI or make a downstream wrapper reconstruct the graph.

Machine-readable status remains valuable for integrations and should be delivered through issue #1210. Until then, a temporary ggrbm shim may use only the documented plumbing commands file, list managed, show up, fork-point, and is-managed. It must not parse presentation-oriented status output or import private Python modules.

Planning must not invoke discover. Discovery is heuristic and can replace a curated layout; initialization and reparenting remain separate, explicit setup operations.

2. Separate planning from mutation

Add a narrow upstream command rather than changing the established meaning of plain traverse. One illustrative interface is: 

git machete restack plan [--from BRANCH] --output PLAN.json
git machete restack apply PLAN.json
git machete restack continue PLAN.json
git machete restack abort PLAN.json

The exact name is an upstream design choice. Extending traverse with an explicit operation allowlist and --plan would also work, provided the allowlist is closed: selecting rebase must exclude pull, reset, push, slide-out, layout edits, and code-hosting actions without relying on a growing set of --no-* flags.

plan must not move refs. Store plans in the common Git directory so every linked worktree sees the same run, for example: 

$(git rev-parse --git-common-dir)/machete/restack/<run-id>/plan.json

The plan should record:

  • repository identity, git-machete version, layout path, and layout checksum;
  • original HEAD branch or detached commit;
  • ordered branch, parent, branch-tip, parent-tip, and fork-point SHAs;
  • the exact commit list that each step will replay;
  • branch-to-worktree mapping and clean/dirty state;
  • detected Git and git-machete hooks;
  • results from configured read-only planning checks;
  • requested mode and every explicit override.

Print the same facts as concise text for a person and JSON for an agent. apply should require the plan path and verify its checksum. An optional --approve <plan-hash> makes it impossible to apply a different plan from the one reviewed. The JSON schema and exit codes become a documented upstream interface, not a local parsing convention.

3. Turn ambiguity into a preflight failure

The upstream planner should classify every edge before applying:

  • Green: parent tip is an ancestor of the child and equals the recorded fork point. The relationship is unambiguous.
  • Red: parent is no longer an ancestor. This is the ordinary restack case. Show the inferred fork point and exact replayed commits in the plan.
  • Yellow: parent is an ancestor, but git-machete’s fork point lies before the parent tip. Stop planning unless the plan receives an explicit fork point or reparenting decision.
  • Strictly merged: child tip is an ancestor of its parent. Mark it skipped. Do not delete it or slide it out.

Fork-point inference is powerful but heuristic. The git-machete fork-point reference says the tool searches reflogs of local and remote-tracking branches and can infer incorrectly when relevant local branches have been deleted. The plan should therefore expose the SHA and commit range rather than silently treating inference as truth.

For a yellow edge, require one of these during planning:

git machete restack plan --fork-point <branch>=<sha>
git machete restack plan --fork-point <branch>=parent
git machete restack plan --skip <branch>

Reparenting changes the branch model and belongs outside the rebase run. This is a deliberate stop, not a request for the agent to guess.

4. Freeze refs and create recovery points

Before the first rebase, apply must verify that the layout checksum and every planned branch tip still match. If any ref changed after planning, invalidate the whole plan.

Create one backup ref per managed branch:

refs/machete/restack/<run-id>/<branch>

Also record the refs in the journal. Reflogs already provide recovery, but named refs make restoring a large set mechanical: 

git update-ref refs/heads/<branch> refs/machete/restack/<run-id>/<branch>

Do not delete backup refs automatically. Report their namespace after completion.

5. Reuse the update engine internally

Implement execution inside git-machete, calling the same internal rebase path used by git machete update. Do not make the new command spawn one git-machete subprocess per branch. Native reuse keeps graph state, hook behavior, worktree transitions, diagnostics, and future fixes in one codebase.

Each step must use the fork point and expected parent tip frozen in the approved plan. This is equivalent to the existing update --fork-point=<planned-old-fork-point> operation, but with compare-before-mutate checks around it. An explicit old fork point prevents a child from carrying its parent’s pre-rebase commits after the parent has moved.

Rebase-only mode must reject a conflicting update=merge annotation rather than silently changing operation type. It must also record and freeze GIT_MACHETE_REBASE_OPTS, or replace that ambient input with options stored directly in the plan.

Before each internal update, verify all of the following again:

  • the current branch tip still equals the expected journal value;
  • the parent tip equals either its original tip or the result recorded by the previous successful step;
  • no Git operation is already in progress, using git rev-parse --git-path rather than assuming .git is a directory;
  • the selected worktree is clean;
  • the branch is still managed and has the same parent;
  • its annotation does not select update=merge;
  • the rebase options environment matches the plan;
  • the exact replay range still matches the plan.

Keep the author-specific ggdcm whitespace policy out of git-machete. During migration, the thin ggrbm shim can run ggdcm <fork-point>..<branch> against every planned range before calling apply. Longer term, expose a generic planning or pre-rebase hook whose non-zero exit blocks mutation; local policy can then live entirely in that hook.

6. Treat worktrees explicitly

Read git worktree list --porcelain during planning.

  • If a branch is already checked out in a worktree, run its update with git -C <path> after confirming that worktree is clean.
  • If it is not checked out, attach it to one temporary worktree owned by the run, update it there, then reuse or remove that worktree.
  • Refuse before any mutation if a required worktree is dirty. Do not stash automatically.

This avoids moving the user’s main checkout between branches and handles the case that plain git rebase <upstream> <branch> cannot check out a branch owned by another worktree. Git-machete’s traverse documentation confirms that worktree placement is already part of its execution model. The new upstream planner should expose that placement in the plan and reuse the same worktree switching machinery during apply.

7. Replace nested shells with a journal

On conflict or hook failure, stop immediately. Record:

  • current step and worktree;
  • expected and actual refs;
  • whether a rebase is active;
  • exact allowed next commands;
  • stdout, stderr, and exit status from the failed command.

git machete restack continue PLAN.json should:

  1. verify that the same rebase is active in the recorded worktree;
  2. run git rebase --continue with editor behavior made explicit;
  3. verify the resulting branch and parent relation;
  4. append the new tip to the journal;
  5. continue with the next planned branch.

abort should abort only the active rebase. Restoring every branch from backup refs should be a separate explicit command because it discards successful conflict resolutions from earlier steps.

Hooks must remain enabled. Silently bypassing pre-rebase, machete-pre-rebase, or repository hooks would defeat project policy. Planning should list executable hooks and fail early if deterministic agent mode cannot guarantee that they are non-interactive.

Keep mixdowns separate

The !branch and !merge escape hatch should not survive migration. It mixes an arbitrary Git program into a file presented as a branch graph.

The existing git mix / git mixdown workflow already owns temporary integration branches. Run it only after a successful rebase run, as a separate command with its own configuration and failure state. This prevents a failed mixdown from being mistaken for an incomplete restack and prevents a rebase plan from acquiring unbounded side effects.

Likewise, remote fetch, pull, reset, push, PR retargeting, branch deletion, and machete layout cleanup should remain separate explicit stages.

Migration path

The current local inventory makes eventual migration small: ten checked-out repositories under ~/.GIT have a .git/machete file, while one has .git/topic-branches. The remaining topic file contains only upstream/branch rebase pairs and no active arbitrary ! commands.

  1. Open an upstream feature request describing the operation allowlist, immutable JSON plan, stale-ref checks, recovery refs, and journaled resume. Link #1210 rather than duplicating its JSON-status scope.
  2. Agree the smallest upstream increment with maintainers and implement it with disposable-repository tests.
  3. While waiting for a release, keep the existing ggrbm unchanged or reduce it only to a thin compatibility and whitespace policy shim. Do not build the full fallback orchestrator unless the upstream proposal is rejected.
  4. Convert the remaining .git/topic-branches relationships into .git/machete, verify every edge, and test the released planning mode without applying it.
  5. Switch ggrbm and ggrbim callers to the upstream command, then retire both wrappers after one successful compatibility cycle.

Implementation choice

Implement the feature in git-machete’s existing Python codebase. The project already has typed domain objects for layouts, branches, fork points, sync status, hooks, and worktrees; those are precisely the objects a reliable planner needs. Keeping the change upstream avoids serializing private state merely so a second program can reconstruct it.

Expose only documented CLI and JSON contracts. Third-party tools should not import git-machete’s private Python modules. A temporary local shim should remain small enough to delete: validate local policy, invoke the upstream plan/apply commands, and relay their exit status.

Suggested exit codes:

0  completed or plan valid
2  usage or invalid plan
3  preflight blocked before mutation
4  conflict or hook failure, resumable
5  refs/layout changed since plan
6  recovery command failed

Every status line should be a single structured event when --format=json is selected. Send diagnostics to stderr and data to stdout.

Minimum test matrix

The upstream feature is ready only when disposable repositories cover:

  • a three-branch stack where the root moved;
  • two sibling branches, proving stable tie-break ordering;
  • a yellow edge that blocks before mutation;
  • an explicitly supplied fork point;
  • a conflict followed by continue;
  • a failure that leaves no rebase state;
  • a branch already checked out in another clean worktree;
  • a dirty required worktree, blocked before any ref moves;
  • a planning-hook failure that blocks before any ref moves;
  • a ref or layout change between plan and apply;
  • interruption after one successful branch and journal-based resume;
  • backup-ref restoration;
  • a merged branch skipped without layout mutation;
  • detached original HEAD restoration;
  • a failing or interactive hook.

Tests should assert ref SHAs, parent relationships, backup refs, journal state, exit codes, and absence of pushes or .git/machete changes. They should not only match human-readable output.

Recommended first increment

Submit a focused upstream proposal before writing implementation code:

  1. Define a closed rebase-only operation set that guarantees no pull, reset, push, slide-out, layout edit, or code-hosting side effect.
  2. Define immutable JSON plan fields and stale-plan validation, building on the machine-readable status discussion in #1210.
  3. Agree whether this is a new restack command or an explicit mode of traverse.
  4. Implement read-only plan generation first, with fixtures and schema tests. Add apply, recovery refs, and journaled conflict resume in reviewable follow-up increments.

Defer subtree selection, interactive rebase, automatic mixdown, and local compatibility code until the upstream contract is accepted. If upstream declines the feature, the original standalone plan/apply orchestrator remains a fallback, not the preferred starting point.

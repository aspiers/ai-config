Which pstack skills are worth using?

A review of all 44 registered skills against recorded AI work, the current cross-agent skill set, and the Beads-first workflow. The two bundled agents, 22 playbooks, and dormant Benny automation pack are covered too.

Short answer

Do not add pstack wholesale to the global skills script. It is a well-designed Cursor orchestration system, but it is not portable as shipped. The best material is a handful of investigation and verification workflows plus several narrow principles. Port those into the tools and authorities already in place.

Recommended path

Port first

  • blast-radius
  • create-verification-skill and maintain-verification-skill
  • why, using Pi MCP discovery and Beads
  • how, using Pi Lens
  • interrogate as a manual deep-review tier

Fold into existing skills

  • prove-it-works into test-running and code-reviewing
  • sequence-verifiable-units into incremental-commits
  • encode-lessons-in-structure into documentation-updates
  • tdd's failing-before evidence rule into test-running
  • The best technical-writing checks into unslop and documentation guidance

Do not adopt unchanged

  • poteto-mode outside Cursor
  • setup-pstack in any non-Cursor harness
  • never-block-on-the-human beside ask-user and human Beads
  • no-comments as a default review step
  • swarm, figure-it-out, and the orchestrator store as parallel task systems

If you want to experience pstack as designed

Install the official pstack plugin inside Cursor and try /poteto-mode there. Do not treat that trial as evidence that the same files belong in .cfg-post.d/skills. The full mode depends on Cursor Task semantics, model slugs, cloud workers, transcript paths, plugin agents, Graphite, Bugbot, and skills from cursor-team-kit.

No installation-script candidate yet

The original Pocock review could recommend a direct install_skills block because most selected skills were ordinary instruction bundles. Pstack is different. Its best workflows need a host port, and its portable principles mostly duplicate local authorities.

All 21 principles

The principle files are the most portable part of pstack. That does not mean installing all of them is wise. Narrow ideas should usually strengthen the existing authoritative skill for that concern.

Principle Score Disposition Assessment
prove-it-works 5.0 Fold into test-running and review Exercise the real artifact and inspect actual outputs instead of trusting compilation or agent summaries. Very strong fit. Existing verification already leans this way, so one authoritative local rule is better than a duplicate skill.
make-operations-idempotent 4.5 Selective import Design mutating commands and loops to recover from retries and partial prior runs. Excellent for configuration scripts, automation, workers, and lifecycle code. Narrow trigger, little conflict.
separate-before-serializing-shared-state 4.5 Selective import Give concurrent actors separate ownership before adding locks or sequencing. Excellent match for Worktrunk and parallel agents. It correctly treats prose conventions as inadequate synchronization.
sequence-verifiable-units 4.5 Fold into incremental commits End each small execution and delivery unit in a check before starting the next. Strong fit with incremental commits, migrations, and test-running. Treat red-first commits as a preferred pattern, not a law.
boundary-discipline 4.0 Adapt Validate external input at boundaries and keep internal business logic typed and pure. Useful, but "trust internal code unconditionally" is too absolute around persistence, plugins, concurrency, and unsafe code.
encode-lessons-in-structure 4.0 Fold into documentation-updates Turn recurring corrections into types, lint rules, checks, metadata, or scripts. Matches the local preference for durable mechanisms. Keep useful explanation and route deferred work through Beads.
minimize-reader-load 4.0 Fold into refactoring skills Cut useless layers and reduce mutable state a reader must remember. Good review heuristic. Do not collapse a boundary that hides real complexity merely to reduce a layer count.
type-system-discipline 4.0 Selective import Use constructive types, parsed boundaries, semantic primitives, and exhaustive variants. Strong in typed projects. Avoid ritual branding or extra precision where it buys no safety.
build-the-lever 3.5 Adapt narrowly Build a rerunnable script, codemod, or generator for work that benefits from repeatability. Great for repeated or audit-heavy work. Requiring a new file for every non-trivial task would generate disposable tooling.
foundational-thinking 3.5 Mine for architecture workflows Choose data shapes, ownership, and shared scaffolding before downstream logic. Sound but broad. Mostly overlaps codebase-design, domain modeling, tests, and concurrency isolation.
guard-the-context-window 3.5 Fold into delegation guidance Send bulk reading to subagents and keep reduced findings in the main thread. Already built into Pi Lens, bounded tools, and subagent practice. The root agent must still inspect decisive primary evidence.
laziness-protocol 3.5 Mine for refactoring skills Prefer deletion, flat call paths, one source of truth, and the smallest complete change. Good antidote to agent overproduction. Smallness is not proof of correctness, and its three-layer heuristic is arbitrary.
migrate-callers-then-delete-legacy-apis 3.5 Use only for proven internal APIs Move every internal caller and delete the old API in the same coordinated wave. Good simplification when caller discovery is complete. Unsafe when external compatibility or release sequencing exists.
model-the-domain 3.5 Mine for codebase-design Replace scattered state assumptions with a structure that owns the invariant. Useful and distinct from Pocock's terminology-focused domain-modeling, but it overlaps existing design and refactoring guidance.
exhaust-the-design-space 3.0 Use for rare high-cost choices Build two or three genuinely different prototypes before choosing a novel design. The installed prototype and architecture skills already cover this. Product preference still belongs to the user.
fix-root-causes 3.0 Redundant Reproduce, instrument, and repair the cause rather than suppressing symptoms. Already covered by diagnosing-bugs and test-running. Its anti-guard stance needs boundary exceptions.
redesign-from-first-principles 3.0 Use with an approval gate Integrate a new requirement as if it had existed in the original design. Can produce a cleaner result, but it tends to widen scope. Consequential redesign needs ask-user.
subtract-before-you-add 3.0 Redundant Remove dead or speculative complexity before building its replacement. Useful sequence, already present in small refactoring and design guidance. Deletion still needs evidence.
experience-first 2.5 Keep as a human product lens Prefer fewer polished features and user experience over implementation convenience. The agent cannot infer delight, scope, or polish priorities. Use it to frame an ask, not to make the product decision.
outcome-oriented-execution 2.5 Do not install globally Accept planned intermediate breakage while a migration converges on its final architecture. Conflicts with independently meaningful commits and checking each unit while the cause is still local.
never-block-on-the-human 1.5 Reject as written Proceed on reversible work and ask only when ambiguity or irreversibility prevents progress. Direct conflict with ask-user and human-owned Beads decisions. The safer rule is to park the dependent decision and continue unrelated ready work.

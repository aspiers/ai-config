Headline finding: collections yes, reusable named groups no

Every candidate can represent or restore a collection of skills in one operation. None provides a mature, first-class, locally declarative abstraction for several reusable, composable named bundles such as next-frontend, security-audit, blockchain, or finance, then applying one or more bundles to a project or global scope.

Vercel’s hosted skills.sh packs are the nearest installable collection, but are not a version-controlled local profile. reskill’s “groups” are registry namespaces and access-control domains, not installable bundles. The other tools treat the entire manifest or lockfile as one environment. Separate manifests/config roots can emulate profiles, but composition, deduplication, conflict policy, and per-group updates remain external work.

This is a material ecosystem gap. A safe group mechanism should expand to a concrete lock that pins every skill independently, preserve per-skill provenance and audit results, deduplicate shared skills and repositories, define conflict semantics, and fail or skip per skill without silently weakening the rest of the group.

Vercel Skills

Verdict: Best ecosystem baseline and agent compatibility, but not a package-lock-grade or security-policy-grade manager. Best for discovering and installing reviewed skills, especially when compatibility matters more than frozen reproducibility.

GitHub stars29,556 as of 2026-08-24
MaintenanceHighly active: 182 commits, 16 releases and 81 merged PRs in the 90-day window
LicenceMIT
Release / commitv1.5.23, 2026-08-18; 435076e

Domain fit

It installs several selected skills from one repository in one invocation and supports every requested agent. Project installs generate skills-lock.json; global installs generate hidden update state. Project restoration groups entries by source, but remains experimental. There is no first-class desired-state manifest, global declarative restore, or local named-profile model. skills.sh pack URLs are installable hosted collections, and Claude plugin manifests provide presentation groups, but neither is a general version-controlled bundle definition.

Security and reproducibility

ATH, Socket and Snyk audit data is useful discovery evidence, but fetching has a short timeout and deliberately returns null on errors; the audit is advisory and --yes installs despite unsafe results. Lock entries record source/ref/path plus a folder hash, not the repository commit. Experimental restoration re-fetches the source and does not enforce the recorded hash. Direct archives receive useful size, traversal, encryption, link and CRC checks. Git-source symlinks are dereferenced during copy, which can expose readable host files through malicious links. No fetched installation hook runs automatically, although agents may later execute scripts shipped inside a skill.

Popularity and maintenance

The canonical repository was not archived and had 29,556 stars. It was by far the largest ecosystem in the shortlist. The latest default-branch commit and v1.5.23 release were both dated 2026-08-18. High issue volume (1,106 open issues/PRs reported by GitHub’s combined counter) reflects scale as well as maintenance burden; no response-time score was assigned.

Licence

The compared CLI is released under the OSI-approved MIT licence, permitting use, modification and redistribution subject to preservation of the licence notice. Individual third-party skills retain their own licensing and trust conditions.

Strengths and trade-offs

Strengths are adoption, broad agent-path support, straightforward multi-skill selection, hosted packs and comparatively careful archive extraction. Trade-offs are fail-open security advice, non-authoritative lock hashes, no persistent Git cache, no general named groups, and best-effort lock writes. It is a good transport/discovery layer but should be wrapped by explicit policy and immutable source pinning for sensitive groups.

reskill

Verdict: The most npm-like declarative user experience and the easiest fit for custom agent targets, but not yet a trustworthy frozen installer. Best for trusted skill sources where manifest ergonomics and broad target configuration dominate.

GitHub stars59 as of 2026-08-24
MaintenanceActive: 32 commits, 2 releases and 15 merged PRs in the 90-day window
LicenceMIT
Release / commitv1.26.0, 2026-08-11; d047721

Domain fit

skills.json declares many sources, selected skills, defaults, registries and custom agents; reskill install can process independent references concurrently and monorepo children together. This gives a strong one-command project environment. Global installs generally skip the project manifest/lock, so declarative global groups are weaker. Despite its terminology, registry “groups” are namespaces, visibility boundaries and member-role domains—not installable bundles or profiles.

Security and reproducibility

skills.lock records the exact commit fetched, but normal reinstall resolves skills.json again rather than restoring that commit, and it records no Git content digest. The persistent cache is keyed by textual source/ref rather than immutable content and can be stale or concurrency-sensitive. The built-in malicious-content scanner blocks high-risk publishing, not ordinary Git, HTTP or registry installation. Registry archives can carry enforced SHA-256/SHA-512 integrity and traversal controls, but empty integrity skips verification; direct HTTP extraction is less constrained. Source URLs and refs are interpolated into shell command strings, which raises command-injection concerns for untrusted manifests.

Popularity and maintenance

The canonical repository was not archived, had 59 stars, and released v1.26.0 on 2026-08-11. Its 32 commits and 15 merged PRs in the activity window indicate continuing development, although the project and its lock semantics remain young.

Licence

The compared CLI is MIT-licensed and qualifies as FOSS. Registry-hosted skills and private registry services can have separate terms; the public comparison covers the open-source CLI.

Strengths and trade-offs

Strengths are the clearest separate intent file, multi-source installation, custom project/global targets, a persistent cache and good monorepo selection. Trade-offs are a non-authoritative lock, no install-time scanner gate for direct sources, cache correctness concerns, and security-sensitive shell/archive handling. It is the easiest basis for manually maintaining stack-specific manifest files, but not the safest executor for untrusted financial, blockchain or security-audit skills.

skiletto

Verdict: The best architectural match for a security-first declarative global/project workflow, provided its early maturity and OpenCode gap are acceptable. Best as a pilot with a machine-owned external scanner such as SkillSpector.

GitHub stars2 as of 2026-08-24
MaintenanceActive but early: 33 commits, 4 releases and 28 merged PRs since creation in the activity window
LicenceMIT
Release / commitv0.4.0, 2026-08-09; 755cbc4, 2026-08-23

Domain fit

skiletto.toml stores intent and skiletto.lock stores exact commit SHAs and content hashes. sync converges every declared source while preserving existing pins; update is the operation that moves them. Project and machine scopes have separate manifests and locks. Multiple skills from one repository share a single resolved snapshot, and a user-wide repository cache avoids repeated clones. The manifest is one collection, but has no named bundle/profile table or profile composition.

Security and reproducibility

A pre-install command configured only in the trusted machine manifest can scan staged content. Non-zero scanner exit aborts before installation or locking; malformed hook configuration fails closed. This avoids letting a cloned project define executable hooks. Exact commits, content hashes and drift refusal provide strong consistency. Caveats: --no-hooks bypasses scanning; editable and already-locked content are not scanned; internal skill symlinks can still point outside the skill; and hash comparison on locked materialization occurs after promotion, so a rare mismatch can replace prior canonical content before erroring.

Popularity and maintenance

The repository was created on 2026-07-01, explicitly labels itself “Early development,” was not archived, and had 2 stars. Nevertheless, 33 commits, 28 merged PRs, four releases and a 2026-08-23 latest commit show intense current development. This is promising activity, not maturity or broad field validation.

Licence

The project is MIT-licensed FOSS. External scanners invoked by hooks have their own licences and data-handling models; an LLM-backed scanner may transmit skill content, whereas an offline static scanner does not.

Strengths and trade-offs

Strengths are clean intent/lock separation, exact pins, hash-based drift handling, machine-level declarative state, cache reuse, no execution of fetched skill code, and a well-designed trusted scanner hook. It supports Claude, Cursor, Codex and Pi, but has no OpenCode/custom-target adapter. It also lacks strict “frozen means do not complete a missing lock” mode and reusable named groups. Its architecture is closest to the requested end state, but adoption should be staged behind tests because the project is only weeks old.

GSKILL

Verdict: Strongest deterministic restoration and structural integrity model. Best for CI and security-sensitive repositories when Claude, Cursor, Codex or Gemini are the required targets; currently a poor fit for Pi/OpenCode-wide global deployment.

GitHub stars3 as of 2026-08-24
MaintenanceVery active, pre-1.0: 164 commits, 11 releases and 51 merged PRs in the 90-day window
LicenceMIT
Release / commitv0.6.0, 2026-08-03; 5fc91c5, 2026-08-19

Domain fit

A versioned skills-lock.json combines user intent with exact commit, version, hashes, target agents and installation mode. install --frozen-lockfile restores all entries without rewriting the lock and fails when required metadata or integrity is inconsistent. Multiple sources in the lock install together; multiple skills can be selected from one source. The commit-keyed shared cache and committed canonical project content support efficient and offline restoration. There is no separate named group/profile abstraction.

Security and reproducibility

This is the strongest built-in consistency design: frozen installs, full commit SHA, multiple content hashes, explicit verification, drift checks, and conservative sync/repair. Discovery does not follow symlinks; escaping symlinks and traversal are rejected; removals are bounded and checked against trusted adapter paths. Fetched skill content is never executed, and release artifacts have checksums, Sigstore material, SBOMs and provenance. The missing piece is malicious-intent assessment: exact hashes faithfully reproduce malicious content too, and there is no scanner hook, publisher signature or trust-policy engine.

Popularity and maintenance

The repository was created on 2026-06-20, was not archived, and had 3 stars. It explicitly warns that CLI and schema changes may occur before 1.0. Its 164 commits, 51 merged PRs and 11 releases show exceptional current development effort, but its tiny user base means limited independent operational evidence.

Licence

The CLI is MIT-licensed FOSS. Its signed binary-release supply chain is a defence-in-depth benefit, but does not attest to third-party skill publishers.

Strengths and trade-offs

Strengths are frozen reproducibility, byte-level integrity, safe path handling, drift visibility, offline cache reuse and excellent documentation. Trade-offs are no semantic scanner, no user-defined adapters, no Pi/OpenCode support, no Windows support, a pre-1.0 schema, and no named groups. It is the strongest substrate if agent coverage is expanded or if a narrower target set is acceptable.

owainlewis/skills

Verdict: A clear and flexible minimalist manifest manager, but not a security-hardened or reproducible package manager. Best only for small sets of trusted, pinned repositories where custom target paths matter.

GitHub stars3 as of 2026-08-24
MaintenanceLow recent activity: 7 commits, 3 releases and 1 merged PR in the 90-day window; latest commit 2026-07-05
LicenceMIT
Release / commitv0.2.1, 2026-05-30; e8cadb3, 2026-07-05

Domain fit

skills.toml is a straightforward source of truth containing many source entries, skill selections, refs, targets and project/global scopes. skills sync processes the collection in one operation and supports custom agent paths, so stack-specific manifests are easy to author. It has no named bundle/profile schema. By default the manifest is user-global, while project entries resolve relative to the current working directory; a committed project manifest requires explicit --config or SKILLS_CONFIG.

Security and reproducibility

Per-target .skills.lock.toml records the installed commit, but ordinary sync resolves the manifest ref again and treats lock state as reporting rather than authoritative input. There is no content hash, frozen mode, installed-file drift check, semantic scanner, hook, executable warning, or persistent cache. Explicitly putting a commit SHA in the manifest is therefore essential for reproducibility. Source subpaths, frontmatter-derived names and recreated symlinks lack the comprehensive adversarial confinement evident in GSKILL.

Popularity and maintenance

The repository was created on 2026-05-30, was not archived, and had 3 stars. Development was much quieter than the other young candidates: the latest release was v0.2.1 on its creation date and the latest commit was 2026-07-05. This may reflect minimalist scope, but there is insufficient evidence of mature adoption or ongoing hardening.

Licence

The project is MIT-licensed FOSS. As elsewhere, installed skills can carry different licences and should be reviewed independently.

Strengths and trade-offs

Strengths are a small understandable codebase, declarative multi-source sync, project/global entries, built-in Pi support and arbitrary custom agents. Trade-offs are fresh clones for every entry/run, moving refs during normal sync, no content verification, no drift defence and weak path/symlink evidence. It offers grouping ergonomics only at whole-manifest level and should not be entrusted with unreviewed security, blockchain or financial skill sets.

Methodology and shortlist

The domain was interpreted as FOSS tools that install Agent Skills-compatible directories and can manage more than one skill. The five candidates were user-supplied through the preceding discussion: Vercel Skills as the incumbent, plus reskill, skiletto, GSKILL and owainlewis/skills. Primary evidence came from each canonical repository at the pinned default-branch revisions linked above, source code, schemas, security/reproducibility documentation, release pages and licence files.

GitHub statistics were observed on 2026-08-24 UTC. The common activity window was 2026-05-24 through 2026-08-24; commit and merged-PR counts are activity proxies, not quality guarantees, and automated commits were not exhaustively removed. Stars measure attention, not fitness. Issue response times were not scored. All five repositories were unarchived and MIT-licensed at observation time.

Smaller wrappers and adjacent projects such as skills-lock, skilled and skillsdock were excluded because the requested set was these five and they offered less complete end-to-end agent/manifest coverage. “Security” was split into malicious-content assessment, source authenticity, deterministic resolution, byte integrity, drift detection, structural path/symlink safety, execution of fetched code, and installer supply-chain controls; no single score can substitute for those distinctions. Source review was bounded rather than a formal penetration test or legal audit.

Comparative recommendation

No candidate completely satisfies the requested combination today. In particular, none has first-class composable named skill groups. Treat group support as a separate desired-state layer that expands named bundles into a fully pinned environment lock.

  1. Pilot skiletto first for global/project declarative management: it best combines exact commits, content hashes, shared repository caching, drift handling and a trusted fail-closed pre-install scanner hook. Validate OpenCode delivery, project-root behavior, internal symlinks and early-version upgrades before migration.
  2. Use GSKILL where integrity outranks agent coverage. Its frozen lock, offline restore, verify/repair workflow and path controls are the strongest. It becomes the leading option if Pi/OpenCode/custom adapters and a scanner hook are added.
  3. Consider reskill only for trusted sources or after hardening. Its skills.json, custom targets and multi-source UX are attractive for group generation, but its lock is not authoritative and its direct-source security model has material weaknesses.
  4. Retain Vercel Skills as ecosystem/discovery infrastructure, or behind the existing fail-closed wrapper, rather than treating its audit and locks as enforcement.
  5. Avoid owainlewis/skills for untrusted groups until it gains frozen restoration, hashes, drift/path hardening and security policy.

For stack/workflow groups, keep a version-controlled catalogue such as next-frontend, security-audit, blockchain and finance, but compile selected groups into a concrete manager manifest/lock before installation. The compiled lock should pin each skill, record provenance and audit disposition, deduplicate repositories, expose conflicts, and be the only input accepted by CI or unattended global installation. This preserves the time-saving value of groups without turning one convenient group name into an unauditable supply-chain wildcard.

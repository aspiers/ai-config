Strategy for reusable AI skill groups

Should the maintainer build skill groups in a friendly fork of Vercel Skills, extend another manager, or keep group semantics in a separate tool? This report compares the options and recommends a companion compiler with a deliberately small downstream patch stack.

Recommendation

Put reusable groups in a companion compiler. Keep a friendly fork only for changes that cannot be implemented outside Vercel Skills.

A conventional long-lived fork gives full control, but it also ties group development to a fast-moving CLI and an unresponsive contribution queue. The group model does not need that coupling. A separate tool can read group definitions, compose them, audit every member, produce a resolved lock, batch members by source, and invoke stock Vercel Skills once per repository.

The other managers do not overturn this recommendation. skiletto and GSKILL have stronger lock and integrity models, but each lacks required agent coverage and still needs a group layer. reskill has the best manifest ergonomics and custom-target support, but its install and lock security is too weak for untrusted sources. owainlewis/skills is pleasantly small and configurable, but would need most of the hardening built from scratch.

This is not a vote against the existing fork. It changes its job. The fork becomes a small patch queue for transport and enforcement gaps such as commit pins, authoritative lock checks, or persistent caching. Group names, group composition, security decisions, and generated locks stay outside it.

Where the other skill managers fit

None has first-class composable named groups. That does not make them irrelevant. Each provides code or design choices worth reusing, and two could become alternate execution backends after the group contract is stable.

The practical order is therefore Vercel Skills for immediate compatibility, skiletto for a second backend experiment, GSKILL as the integrity benchmark, reskill as a manifest UX reference, and owainlewis/skills as a minimalist syntax reference. The group catalogue should not depend on any one of them.

Why a full fork is the wrong default

The maintenance signal is bad

  • The maintainer's audit-results branch feat/surface-audit-results contains one downstream commit and is already 144 upstream commits behind.
  • The corresponding contribution has received automated review but no maintainer response after three direct review requests.
  • Upstream ships frequently. A fork must absorb changes in discovery, source parsing, locks, agents, authentication, archive handling, and update behavior.

The desired model does not belong in transport code

  • Groups are user intent. Installation is an execution detail.
  • A group may contain skills from several repositories and may include other groups.
  • The resolved lock should survive a future move from Vercel Skills to skiletto or another backend.
  • Security policy should reject one member without silently changing the trust policy for its siblings.

Proposed design

Keep the input model small and explicit. A versioned group catalogue records intent. A generated lock records the exact resolved environment. Only the lock is accepted for unattended installation.

Processing flow

  1. 1. Read groups Load named groups and recursively expand included groups.
  2. 2. Resolve Normalize source, path, ref, agent targets, and scope for every skill.
  3. 3. Audit Apply policy to each skill. Rejected or unverifiable members remain explicit.
  4. 4. Lock Record commit, content hash, provenance, audit disposition, and selected groups.
  5. 5. Plan Deduplicate skills, expose conflicts, and batch allowed members by source and ref.
  6. 6. Apply Call stock Vercel Skills once per batch, then verify the installed state.

Ownership boundary

The companion tool owns

  • Group definitions and recursive composition
  • Cycle, duplicate, and conflict handling
  • Security policy and audit exceptions
  • Source and commit resolution
  • The generated environment lock
  • Batch planning, drift checks, and reconciliation

Vercel Skills owns

  • Repository and skill discovery
  • Agent path knowledge
  • Copy and symlink installation behavior
  • Interactive UX when explicitly requested
  • Ecosystem compatibility and new agent support

How to keep the friendly fork manageable

Keep the fork, but treat it as a tested patch queue rather than a separate product. Do not put group definitions or the group schema on the fork's main branch.

  1. Maintain one branch per downstream change, each rebased directly onto upstream main.
  2. Keep each patch independently testable and removable. Record the upstream issue or pull request it replaces.
  3. Run scheduled rebase and test jobs. A conflict should fail visibly rather than leaving an old fork installed.
  4. Build a downstream release branch by applying the patch branches in a fixed order.
  5. Delete a patch as soon as upstream provides equivalent behavior. The companion lock must continue to work before and after that deletion.

Likely patch candidates are commit-SHA transport support, enforced lock verification, and persistent repository caching. Group composition is not a patch candidate because it belongs above the installer.

Risks and controls

CLI coupling

Calling a CLI is less stable than a library API. Keep the adapter narrow, pass explicit flags, avoid parsing decorative output, and test against a pinned supported Vercel Skills version.

Two lock formats

Vercel Skills writes its own state. Treat the companion lock as authoritative and the backend lock as observed execution state. Verify agreement after each apply.

Audit service failure

An unavailable or malformed audit must reject the affected member unless an explicit reviewed exception exists. It must not block unrelated allowed members.

Backend replacement

Keep backend-specific fields out of group definitions. Store normalized provenance and content hashes in the resolved lock so another adapter can consume the same plan.

Decisions still needed

The architecture can proceed once these choices are made. They are listed separately so they can be discussed without another dense questionnaire preamble.

  1. Primary direction. Confirm companion compiler first, or choose a full downstream fork despite the maintenance cost.
  2. Implementation language. A shell and jq prototype would extend the current installer quickly. TypeScript would reuse Vercel Skills types and libraries more easily. Python would make the compiler and tests independent of the Node toolchain.
  3. Lock authority. Decide whether the first release must pin exact commits and content hashes, or whether that can follow a dry-run group compiler.
  4. Fork threshold. Define which failed backend conformance tests justify a downstream patch. This prevents convenience changes from accumulating in the fork.

Proposal: a plan-enabled git machete traverse

Proposal dated 7 September 2026

⚠️ AUTHOR-SPECIFIC SCOPE: This report analyzes the maintainer's deployed ~/bin/ggrbm and current local checkout inventory. The proposal is reusable, but that path and the inventory observations are specific to this setup.

Status: This document proposes an upstream design. It does not describe an implemented git-machete feature, accepted command names, or a committed delivery schedule.

Recommendation

Propose a planning layer for git machete traverse upstream, then replace ggrbm with it. The design should combine git-machete's branch graph and existing traversal choices with an inspectable plan, exact stale-input checks, recovery refs, conflict journaling, optional remote synchronization, and optional pull-request or merge-request updates.

This should not turn plain git machete traverse into a different command. Without a planning option, its user-visible behavior should remain unchanged. The new lifecycle is explicit: create or edit a plan, refresh it, inspect it, and apply that exact plan.

Git-machete already owns the difficult parts: branch layout, fork-point inference, parent-before-child traversal, update modes, qualifiers, hooks, and linked-worktree handling. Rebuilding those rules in a large local script would create a second orchestration engine that drifts from upstream. The right goal is not to make git-machete imitate ggrbm. It is to give traverse a safer and more capable planned mode.

What is wrong with ggrbm

The current ggrbm has served since 2009, but its control model assumes a person is at a terminal. Its useful idea is simple: update related branches in a known order and stop when a replay needs attention. Its implementation now duplicates state and leaves too much implicit.

Current behavior Problem
Reads ordered git rebase arguments from .git/topic-branches Duplicates the branch graph in .git/machete and cannot validate cycles, repeated branches, or parent order
Launches a nested shell after failures or conflicts Hides execution state from callers and provides no structured resume point
Prompts while mutation is already in progress Makes unattended use unsafe and can discover a blocking decision after earlier refs have moved
Accepts arbitrary !git ... commands Gives a branch-update file unbounded checkout, ref, merge, and remote side effects
Relies on reflogs and operator memory for recovery Creates no named backup refs, run journal, or mechanical rollback

Concrete failure cases make a direct rewrite unattractive:

  • A failed git rebase that leaves neither rebase-apply nor rebase-merge can be reported as finished, after which processing continues.
  • The initial in-progress check examines only $root/.git/rebase-apply. That misses the merge backend and does not handle linked-worktree Git paths correctly.
  • The custom file cannot reject a stale ref, child-before-parent entry, duplicate branch, cycle, or repeated update before mutation starts.
  • The script may discover a dirty worktree or invalid branch only after previous branch refs have moved.

The replacement should preserve the intent, not the accidental interface. Arbitrary Git commands do not belong in a traverse plan, and mixdown remains a separate workflow. Core git-machete and the default compatibility shim should contain no ggdcm or whitespace policy. Repositories can enforce such policy through their existing Git and git-machete hooks.

Plain traverse stays plain

Today's git machete traverse walks the layout, updates branches, understands worktrees, and offers interactive or --yes operation. It can rebase, merge, fast-forward from a remote, handle diverged remote state, push, and slide merged branches out of the layout according to its options and prompts. Those existing semantics should remain intact when no plan option is present.

Planned traversal adds a contract around the same domain model. It does not make rebase the only legitimate update. It supports rebase and merge, including Git's interactive and non-interactive rebase forms. An unattended apply rejects interactive rebase steps because they require live human input.

Keep every current traversal scope choice. With no option, traversal starts from the current branch. --start-from continues to accept here, root, first-root, or a branch name. Preserve --stop-after, --whole, and -W, where -W means a pre-plan fetch followed by whole-layout planning. If upstream adds a subtree selector, it is additive. It must not replace or narrow those choices.

Upstream research

The upstream tracker contains pieces of this design but not the full plan/apply workflow. Open issue #1210 requests machine-readable JSON status. A maintainer invited a pull request and recognized that integrations need stable plumbing instead of access to private Python objects. The event stream proposed here can build on that work without treating status JSON as a saved plan.

Closed issue #293 introduced traverse branch qualifiers such as rebase=no and push=no. Closed issue #1619 and merged PR #1626 concern safer traversal when local and remote branches disagree. They are evidence that planned safety belongs in traversal itself, but none supplies the complete design in this report.

A search found no existing issue or open pull request for this full proposal. That is not proof that no related discussion exists. An upstream proposal should cite #1210, #293, #1619, and PR #1626, and should separate overlapping work rather than claiming a blank slate.

Illustrative interface

The following syntax explains the lifecycle. Exact command and option names are for upstream discussion, not a claim about the current CLI: 

git machete traverse plan [--start-from WHERE | --whole | -W] \
  [--stop-after BRANCH] [--subtree BRANCH] [--fetch] \
  [--output PLAN.yaml]

git machete traverse plan refresh PLAN.yaml
git machete traverse apply PLAN.yaml
git machete traverse apply PLAN.yaml --unattended \
  --expected-plan-hash SHA256 --yes
git machete traverse continue PLAN.yaml
git machete traverse abort-step PLAN.yaml
git machete traverse rollback PLAN.yaml
git machete traverse backup prune RUN-ID

plan gathers facts but moves no local branch refs and performs no pushes or hosting-provider API calls. It may fetch only when the caller asks it to, and only before it computes the plan. There is no implicit fetch between planning and apply. A caller that wants fresher remote refs must fetch and create or refresh a new plan.

Saved plans are YAML because people must be able to read and edit choices. Structured machine and agent event streams are JSON, one event per record, with documented schemas and exit codes. JSON status output and YAML plans solve different problems and should not be conflated.

Plan model and integrity

Plan state defaults under the Git common directory, for example $(git rev-parse --git-common-dir)/machete/traverse/<run-id>/. Every linked worktree can therefore see the same plan, journal, and backup inventory. Git-machete generates the run ID as a computed, non-editable identifier. Creating a run fails atomically if either its state directory or backup-ref namespace already exists.

The YAML separates editable choices from computed facts. Choices include update methods, yes/no/ask policies, fork-point corrections, qualifier overrides, worktree handling, remote actions, and ordering. Computed facts include SHAs, commit lists, layout and configuration fingerprints, hook inventory, resolved worktrees, and remote expectations. After a person edits a choice, plan refresh recomputes every dependent fact and invalidates the old plan hash. 

version: 1
run_id: 20260907T120000Z-example
choices:
  ordering: local-then-push-then-hosting
  branches:
    topic/example:
      update: rebase
      unusual_replay_range: yes
      push: yes
computed:
  layout_hash: sha256:...
  branch_tips:
    topic/example: 0123456789abcdef...
  replay_commits:
    topic/example:
      - 89abcdef01234567...

The plan hash is the SHA-256 digest of the exact saved YAML bytes and is not embedded in the file it hashes. Apply reads the file once, hashes that byte buffer, and parses and executes the same buffer. It must not reopen the path after verification. Git-machete stores no approval state. Interactive apply calculates and displays the digest with the refreshed plan, then asks for confirmation at apply time. Unattended apply requires the caller to provide the expected digest. This binds apply to the file selected by the caller. It does not authorize the caller, grant repository permissions, or replace operating-system and hosting-provider authentication.

The general policy for an action is yes, no, or ask. Interactive planning may replace ask with a saved choice. Interactive apply may instead leave it intact and ask at the planned branch; the hash then covers a deliberate delegation to one of the precomputed choices, not a final yes or no. The runtime answer is appended to the journal without rewriting the plan. Unattended apply rejects every unresolved ask. --yes skips confirmation only for an already resolved plan with the expected hash. It never chooses update methods, remotes, resets, force-pushes, qualifier overrides, fork points, or any other missing decision.

Actions a plan can contain

A plan uses a typed action vocabulary rather than arbitrary shell or Git commands. Core actions therefore have finite validation, preview, stale check, journal, and rollback rules. Existing hooks remain trusted, unbounded extension points; their side effects cannot generally be predicted or rolled back by the plan.

Local update actions

  • Rebase. Record branch tip, parent tip, fork point, exact commits to replay, rebase options, and whether Git runs in interactive or non-interactive mode. Interactive mode is valid only for attended execution.
  • Merge. Record the branch, parent, expected tips, merge options, expected fast-forward or merge-commit behavior, and whether an attended run may open the merge-message editor. Unattended apply requires no-edit behavior. Preserve the invocation-wide --merge option and any recognized update=merge annotation. Planned mode also records the resolved update method for each branch.
  • Fast-forward from a remote-tracking ref. A local branch that is behind can move forward through an explicit planned action. The plan records old local SHA, target remote-tracking SHA, and remote-ref expectation.
  • Reset a diverged local branch. This is an explicit per-branch choice. Show the commits unique to the local branch and the commits unique to the remote-tracking branch. Present no action, reset-local, and force-push-remote as explicit choices. Never use commit timestamps to recommend one. Record old and target SHAs, and create the backup ref before the reset.
  • Autostash. Dirty worktrees block by default. A plan may explicitly create and later restore a stash for a named worktree, with failure handling in the journal.

Remote actions

  • Push. Pushes are optional planned actions, never an automatic consequence of a local update. Record the remote, destination ref, and expected destination SHA. If an earlier rebase or merge will generate the source commit, record a dependency on that action rather than an impossible future SHA. Apply resolves the dependency from the journal and pushes that exact object ID.
  • Force-push. Resolve it separately for each branch and display the exact protection: --force-with-lease=refs/heads/<destination>:<expected-sha>. Interactive plan or apply may ask when the choice is unspecified. Unattended apply requires the choice and lease SHA to be resolved.
  • Publish an untracked branch. A branch with no upstream needs an explicit publish action containing the remote, source and destination refspec, and the tracking configuration change to make after a successful push.

Layout and hosting actions

  • Slide out a merged branch. Existing merge detection may offer this as an optional plan or interactive action. Sliding out reparents the branch's children in the machete layout. It does not delete the Git branch. Detection alone never performs the change.
  • Create or retarget a pull request or merge request. Hosting-provider API actions are an optional final phase. Each action records provider identity, repository, head, base, stale-state expectations, and a stable operation ID where the provider supports one. Credentials stay outside the plan. After a timeout or unknown result, apply queries provider state before retrying or generating a compensating action; it never retries blindly.

Keep the existing merge-detection modes configurable and retain simple as the default. Detection can only offer a slide-out action. The action still needs yes or an attended answer.

The default phase order is deliberate: finish all selected local branch updates, then perform pushes, then call pull-request or merge-request APIs. This keeps local graph repair separate from externally visible changes. Branch-by-branch local-update-and-push ordering remains an optional plan choice for workflows that need it.

Mixdown is not an action type. The existing git mix/git mixdown workflow should run separately after traversal. A plan must reject arbitrary git or shell commands, including the old !branch and !merge escape hatch.

Ambiguity, fork points, and qualifiers

Fork-point inference is useful but heuristic. The fork-point documentation explains that git-machete searches local and remote-tracking reflogs and can infer incorrectly after relevant branches disappear.

When git-machete infers an unusual replay range, the situation commonly shown as a yellow edge, the plan should avoid color as the explanation. It should state that the inferred fork point predates the current parent tip, print the fork-point SHA, parent and child SHAs, and list every commit to replay. Planning then requires explicit approval of that range or a corrected fork point. It must not guess from graph color or continue unattended.

Branch qualifiers such as rebase=no, push=no, and slide-out=no block the corresponding action by default. A plan may override a qualifier only for a named branch through an explicit choice. The rendered plan, YAML choice section, event stream, and journal must record the override prominently. A global --yes cannot override qualifiers.

Worktrees, hooks, and checkout return

Planning reads git worktree list --porcelain. If a selected branch is already checked out, the plan targets that worktree. A branch not checked out anywhere defaults to a temporary worktree owned by the run. Existing choices for operating in the current worktree, switching worktrees, or using configured worktree behavior remain available and appear in the plan.

Dirty worktrees block by default before their first affected mutation. Explicit planned autostash is allowed. The plan identifies the worktree, stash timing, and restoration policy. An unattended apply must not improvise a stash because it encounters dirt.

Planned mode defaults to returning to the checkout where the run began, including a detached HEAD. All current return choices remain configurable. Temporary worktree cleanup and checkout restoration are journaled steps so failure does not masquerade as a completed run.

Existing Git and git-machete hooks remain usable. The plan fingerprints relevant hook and configuration inputs, including executable hook files and options that affect update behavior. Hooks are arbitrary programs, so fingerprinting does not make their side effects deterministic. Unattended apply closes standard input and disables Git's terminal and editor prompts. A hook can still open /dev/tty, sleep, or mutate state outside the action model, so unattended hook execution also needs a configurable timeout recorded in the plan. Preserve each hook's existing failure semantics: operation-hook failures stop and journal the run, while informational status-hook failures remain non-fatal. A post-slide-out hook fails after the layout mutation and must therefore leave enough journal state for guarded restoration. The design adds no core or default-shim whitespace check.

Staleness rules

Plan-enabled apply takes a lock in the Git common directory to prevent two planned runs from operating concurrently. That lock cannot control ordinary Git commands or hooks, so every mutation still needs an atomic guard. Ref updates compare the current object ID with the expected old ID. Layout changes use a lock file, verify the expected layout hash, and replace the file atomically. Apply rechecks affected state after hooks and before the next mutation.

Before each affected mutation, apply compares current inputs with the computed plan facts. A stale local branch ref, remote-tracking ref, layout, qualifier, relevant option, hook, or configuration input fails before that mutation and requires an explicit replan. Apply never silently recomputes a fork point, replay range, lease, worktree choice, update method, or action policy.

A partially completed run is not refreshed in place. The operator must first finish or abort any active Git operation. A replan-remaining command then creates a successor plan whose immutable prefix cites the completed journal entries and whose newly computed suffix covers only unfinished actions. It gets a new run ID and hash. Interactive execution confirms that successor at apply time; unattended execution supplies its expected hash. No implicit fetch occurs during this process.

Backups, conflicts, and recovery

Every plan-enabled apply creates backup refs before its first mutation under refs/machete/backups/<run-id>/.... The plan records the complete backup set. Apply creates the namespace with no-clobber ref transactions and fails if any target backup ref already exists. Back up each local branch that the plan can move, including branches subject to reset, rebase, merge, or fast-forward. Plans that contain only remote or API actions still create anchor refs in the run namespace. Only an explicit backup-prune operation removes these refs. Completion, abort, and rollback do not prune them.

Planned runs use a durable write-ahead journal. Before an action, append and flush an intent record containing its expected inputs. After the mutation, inspect actual state and atomically append and flush its result. On restart, an intent without a result is reconciled against refs, Git operation state, layout, remote state, or provider state before any retry. The journal also records conflicts, hook failures, generated commits, stashes, worktree moves, pushes, and API results. Plain immediate traverse remains stateless and keeps its current conflict behavior. The persistent journal belongs only to plan/apply mode.

traverse continue is explicit. It verifies the recorded Git operation and worktree, checks all still-relevant facts, continues the current rebase or merge, records its resulting SHA, and advances to the next planned action. An interactive rebase can continue only in an attended session.

Recovery has two different commands. Abort-current-step applies only while an abortable Git operation, such as rebase or merge, is active; it invokes that operation's abort command. Completed fast-forwards, resets, and slide-outs have no native abort operation. Full local rollback uses backup refs plus the pre-run layout snapshot stored in the journal to restore all local ref and layout changes.

Rollback must use guarded ref updates. By default, each current ref must still equal the post-action SHA in the journal, each affected checked-out worktree must be clean, and the current layout must match the journaled post-action hash. It also restores or reports every journaled stash, checkout move, and temporary worktree; failure to restore one leaves the rollback incomplete rather than silently declaring success. If newer local work exists, rollback stops. An explicit per-branch override may replace that newer state only after creating a further backup and showing the exact refs and layout bytes to restore.

Local rollback cannot pretend to undo a push or hosting-provider API call. Remote restoration requires a separate compensating plan. That plan reads current remote refs, obtains new explicit lease checks, and describes reverse pushes or API changes as new actions. It never reuses an old lease or silently rewinds a remote.

Execution inside git-machete

Implement planning and execution in git-machete's existing Python codebase. Reuse the internal graph, fork-point, update, qualifier, hook, merge-detection, and worktree machinery. Do not spawn one git-machete subprocess per branch, parse presentation-oriented status output, or ask a wrapper to import private Python modules.

A documented YAML plan schema, JSON event schema, and exit-code contract are appropriate public interfaces. A possible exit-code set is: 

0  completed, or plan valid
2  usage error or invalid plan schema
3  unresolved choice or preflight block before mutation
4  conflict or hook failure, resumable
5  planned input became stale, replan required
6  abort or local rollback failed
7  remote or hosting action failed

These numbers are illustrative too. The contract matters more than the exact values: JSON events go to standard output, diagnostics go to standard error, and automation should not scrape prose.

Migration path

The existing author-specific inventory suggests a small eventual migration: ten checked-out repositories under ~/.GIT have a .git/machete file, while one has .git/topic-branches. The remaining topic file contains only upstream/branch rebase pairs and no active arbitrary commands. These figures describe one checkout inventory, not a general installation assumption.

  1. Open one upstream design issue for plan-enabled traverse. Link #1210, #293, #1619, and PR #1626, and state that plain traverse is unchanged.
  2. Agree the full design upstream, then deliver it through incremental pull requests. Start with plan schema and read-only generation, then stale checks and backups, local apply and recovery, remote actions, and hosting-provider actions.
  3. Keep ggrbm as a small compatibility wrapper while those increments ship. The default wrapper translates scope and policy, invokes upstream commands, and relays exit codes. It does not retain ggdcm or whitespace checks.
  4. Convert the remaining .git/topic-branches relationships to .git/machete, verify every edge and qualifier, and test generated plans without applying them.
  5. Run attended apply cycles, then unattended cycles with expected plan hashes. Retire ggrbm and ggrbim only after compatibility is proven.

Upstream acceptance should cover the complete model even though code arrives in smaller reviews. This avoids an early rebase-only contract that later has to be broken to represent merge, remote, slide-out, or hosting actions.

Minimum test matrix

Disposable repositories should cover at least:

  • default current-branch scope, every --start-from value, --stop-after, --whole, -W, and additive subtree selection;
  • rebase, merge, non-interactive rebase, attended interactive rebase, edited merge messages, no-edit merges, and unattended rejection of editor-dependent updates;
  • parent-before-child ordering, stable sibling order, and optional branch-by-branch remote ordering;
  • an unusual inferred replay range that lists commits and blocks until approval or a corrected fork point;
  • qualifier blocking and a prominent explicit per-branch override;
  • merge detection in every existing mode, with simple as default and no slide-out before approval;
  • slide-out reparenting children without deleting the Git branch;
  • a branch behind its remote, a diverged reset with unique commit lists, a normal push whose source depends on a generated update result, a force-push with exact destination lease, and publication with tracking setup;
  • fetch before planning and proof that no fetch occurs between plan and apply;
  • plan YAML editing, refresh, old-hash invalidation, hashing and parsing the same byte buffer, interactive apply-time confirmation, unattended expected-hash checking, and rejection of colliding run IDs or backup namespaces;
  • no unresolved ask in unattended mode and proof that --yes invents no choice;
  • stale local ref, remote ref, layout, qualifier, option, hook, and config input, each failing before its affected mutation, plus racing updates rejected by guarded ref or layout writes;
  • a branch in another clean worktree, a temporary worktree, a dirty block, explicit autostash, detached HEAD, and every return choice;
  • existing operation and status hooks, post-slide-out hook failure, closed standard input, disabled Git prompts, and timeout handling in unattended mode;
  • crashes before and after every mutation boundary, reconciliation of a write-ahead intent without a result, conflict journal and continue, active-operation abort, successor planning for unfinished actions, guarded full local rollback with layout snapshots, persistent backups, explicit prune, and refusal to overwrite newer local work by default;
  • compensating remote restoration with fresh lease checks;
  • all-local-then-push-then-hosting default order, provider failure or unknown result followed by state reconciliation, and absence of credentials from plans and events;
  • rejection of arbitrary Git commands and proof that plain immediate traverse remains behaviorally unchanged and journal-free.

Tests should assert exact ref SHAs, unique and replay commit lists, parent relationships, layout changes, backup refs, worktree and stash state, journals, plan hashes, JSON events, API requests, exit codes, and the absence of unplanned fetches or remote mutations. Matching prose is not enough.
